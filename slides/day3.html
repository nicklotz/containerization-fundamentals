What an orchestrator does

  • Scheduling picks a node for each container, based on the CPU and memory it requests
  • Self-healing restarts failed containers and replaces them when a node fails
  • Scaling runs more or fewer copies of a service
  • Service discovery and load balancing give a set of copies one stable name and address
  • Rollouts and rollbacks replace a version step by step and can return to the previous one

Docker Engine runs containers on one host. An orchestrator manages them across a cluster of hosts (Kubernetes Authors, 2026).

Start from what the students already know. On Days 1 and 2, Docker did these jobs on one machine, and you did the rest by hand. Restart policies brought containers back after a crash, and you ran docker compose up with --scale when you wanted three scanners. An orchestrator does the same jobs for many machines, and it keeps doing them without a person watching. ECS is also an orchestrator. Its service scheduler keeps the desired number of tasks running and replaces failed ones. Kubernetes does the same with Deployments. The Kubernetes overview page lists these capabilities, along with storage orchestration, batch execution and configuration management, which come later today. Ask the class which of the five they did by hand on Day 2. Source: Kubernetes Authors (2026), Overview.

What a scheduler does

The scheduler compares each Pod's requests with the CPU and memory that are not yet reserved on each node. It ignores current usage (Kubernetes Authors, 2026).

kube-scheduler watches for Pods that have no node assigned. For each one it runs two phases. Filtering removes nodes that cannot run the Pod: too little unreserved CPU or memory for its requests, a taint the Pod does not tolerate, a node selector that does not match, or a volume in another zone. Scoring ranks the remaining nodes with plugins, for example one that balances resource use and one that spreads Pods of the same app across nodes. The highest score wins, and ties are broken at random. The scheduler then binds the Pod by recording the node name. It never starts containers; the kubelet on that node does. Because only requests count, a Pod without requests looks free to the scheduler, which is why the Pod lecture asks you to set them. Borg used the same two steps, which its paper calls feasibility checking and scoring (Verma et al., 2015). Source: Kubernetes Authors (2026), Kubernetes Scheduler.

From Borg and Omega to Kubernetes

Each system kept the ideas that worked in the one before it (Burns et al., 2016). In 2015, Borg ran hundreds of thousands of jobs on clusters of up to tens of thousands of machines (Verma et al., 2015).

Kubernetes did not start from nothing. Google ran its services and batch jobs on Borg, and the Borg paper describes clusters of up to tens of thousands of machines. Omega was a later redesign. It kept the cluster state in one shared store and let several schedulers work in parallel, and many of its ideas went back into Borg. Kubernetes was the third system. Google released it as open source in 2014, version 1.0 followed in 2015, and Google gave it to the newly formed Cloud Native Computing Foundation. Burns and colleagues list lessons that Kubernetes took from the first two: group containers into Pods, give every Pod its own IP address, identify things by labels instead of numbers, and send every component through one API. Ask the class why a company would give away the design of its internal platform. Sources: Verma et al. (2015); Burns et al. (2016).

Desired state and reconciliation loops

You declare what you want in the spec. Controllers act until the status matches it (Kubernetes Authors, 2026).

This is the central design idea of Kubernetes. You do not tell the cluster to start three containers. You store an object that says three replicas should exist, and a controller compares that with what it observes. If one Pod is missing, it creates one. If there are four, it deletes one. It repeats the check whenever something changes and also at intervals, so it recovers from events it missed. The documentation compares a controller to a thermostat, which switches the heating on and off until the room reaches the temperature you set. Burns et al. (2016) describe Kubernetes as many small control loops, each reconciling one kind of object, with no central program giving orders. BagTrack example: in Lab 08 you delete a bag-api Pod and watch a replacement appear. Ask the class which controller notices the deleted Pod first, and what it does. Source: Kubernetes Authors (2026), Controllers.

Labels and selectors

Labels are name=value pairs on any object. Services, Deployments and kubectl find objects by selecting on their labels (Kubernetes Authors, 2026).

Labels are how Kubernetes objects find each other. A label is a name=value pair, and a selector is a query over labels. The Service on this slide sends traffic to every Pod with app=bag-api, whoever created it. The board Pod has a different label, so it is not selected. Version labels let two versions run side by side behind one Service, which is how the rolling updates later today work. This loose coupling came from Borg experience. Borg grouped tasks into jobs and identified them by job name and index number, which made it hard to describe groups that cut across jobs; Kubernetes uses labels instead (Burns et al., 2016). A common mistake is a typo in a selector. The Service then has no endpoints, and calls from the board to bag-api fail. Ask the class what happens if a debug Pod that you start by hand gets the label app=bag-api. Source: Kubernetes Authors (2026), Labels and Selectors.

The control plane

Every component reads and changes cluster state through the API server (Kubernetes Authors, 2026).

The control plane is the part of the cluster that makes decisions. kube-apiserver is the only entry point to the cluster's state. It authenticates each request, checks the object against its schema and the admission rules, and stores it in etcd. etcd is a consistent, replicated data store that holds every object in the cluster. kube-scheduler and kube-controller-manager never talk to each other. They watch the API server for changes and write their results back to it. The controller manager bundles many controllers, such as the ReplicaSet, Deployment, Job and EndpointSlice controllers. On EKS, AWS runs all of these components for you. In your k3s cluster they run inside one k3s server process, and with one server k3s stores the data in SQLite through kine instead of etcd (K3s Project Authors, 2026). Ask the class whether running Pods stop when the API server is down. They do not. Nodes keep their containers running, and only changes stop. Source: Kubernetes Authors (2026), Cluster Architecture.

What runs on every node

The kubelet talks to the container runtime through the Container Runtime Interface (CRI). Kubernetes removed its built-in Docker support in version 1.24 (Kubernetes Authors, 2026).

Every node, including the k3s server in your lab, runs three node components. The kubelet watches the API server for Pods assigned to its node, asks the container runtime to start their containers, runs their probes, and reports status back. It talks to containerd through the Container Runtime Interface, a gRPC API. This is the same containerd you met under dockerd on Day 1, with no dockerd in between. kube-proxy watches Services and EndpointSlices and writes packet-forwarding rules; the Services lecture looks at those rules. The CNI plugin gives each Pod a network interface and an IP address that every other Pod can reach. k3s uses flannel by default. EKS uses the Amazon VPC CNI, which gives Pods IP addresses from the VPC's subnets. Ask the class whether docker ps on the VM will show bag-api's container. It will not. docker ps shows the k3d node containers, and bag-api runs inside one of them, under that node's containerd. Sources: Kubernetes Authors (2026), Node components; K3s Project Authors (2026).

You write apiVersion, kind, metadata and spec. The cluster adds status, which kubectl get pod bag-api -n bagtrack -o yaml shows (Kubernetes Authors, 2026).

Every Kubernetes object has the same four top-level fields that you write. apiVersion and kind say which API type this is. Pods are in the core group at version v1, Deployments are apps/v1 and CronJobs are batch/v1. metadata holds the name, the namespace and the labels; the labs keep BagTrack in a namespace called bagtrack. spec is the desired state. The fifth field, status, is written by the controllers and the kubelet, and you never put it in a file. You send manifests with kubectl apply -f, which creates the object or updates it to match the file. Keep manifests in Git next to the code, the same habit as keeping the Dockerfile and compose.yaml in the repository. kubectl explain pod.spec.containers prints the documentation for any field, served by the API server itself. Ask the class what the ports field does, given that every Pod has its own IP address. It is mostly informational. It names the port, and leaving it out does not block traffic. Source: Kubernetes Authors (2026), Objects in Kubernetes.

How k3d runs a cluster on your lab machine

k3d runs each k3s node as a Docker container (k3d Authors, 2026). Pods run inside those containers, under each node's own containerd.

This is the cluster you build in Lab 07. k3d is a small tool that runs k3s inside Docker, and k3s is a fully conformant Kubernetes distribution packaged as a single binary. The Pod is the unit of scheduling

The scheduler places a whole Pod on one node. Its containers share the Pod's network namespace and can share volumes (Kubernetes Authors, 2026).

A Pod is the smallest thing Kubernetes schedules. It is a group of one or more containers that always run together on the same node. They share one network namespace, so they have one IP address and reach each other on localhost. That is also why two containers in one Pod cannot listen on the same port. They can also mount the same volumes, so one container can read files that another writes. On Day 1 you looked at namespaces in /proc/<pid>/ns; a Pod is a set of containers that join the same network and IPC namespaces. Burns et al. (2016) describe the Pod as the Kubernetes version of Borg's alloc, a resource envelope that held a main program and its helpers. Most Pods have a single container. In Lab 07 you run the scanner next to bag-api in one Pod, and the scanner calls http://localhost:8000. Ask the class what would have to change if the two ran in separate Pods. Source: Kubernetes Authors (2026), Pods.

The Pod lifecycle and restart policy

Before each restart the kubelet waits twice as long as before, from 10 seconds up to 300. While it waits, the container shows CrashLoopBackOff (Kubernetes Authors, 2026).

A Pod's phase is a summary. Pending means the API server accepted the Pod but it is not running yet. It may be waiting for the scheduler, or the node may still be pulling the image. Running means it is bound to a node and at least one container is running or restarting. Succeeded and Failed are end states, which matter for Jobs. restartPolicy applies to all containers in the Pod. Deployments require Always; Jobs use OnFailure or Never. When a container keeps exiting, the kubelet doubles the delay before each restart, up to five minutes, and resets it after ten minutes of normal running. During the wait the container is in the Waiting state with the reason CrashLoopBackOff, while the Pod phase stays Running. On deletion, the kubelet sends SIGTERM, waits 30 seconds by default, and then sends SIGKILL, which matches the exit codes 143 and 137 from Day 1. Ask the class what kubectl get pods shows for a container that exits with code 1 every time it starts. Source: Kubernetes Authors (2026), Pod Lifecycle.

Liveness, readiness and startup probes

ProbeQuestion it answersWhen it failsbag-api
LivenessIs the process still working?The kubelet restarts the container/healthz
ReadinessCan it serve requests now?The Pod leaves the Service's endpoints until it passes/readyz, which also checks Postgres
StartupHas the app finished starting?The kubelet restarts the container. The other probes wait until it passes.Not needed

Liveness should check only the process itself. If it also checked Postgres, one database outage would restart every bag-api Pod (Kubernetes Authors, 2026).

Probes tell the kubelet whether your app works, because a running process is not always a working one. A probe can be an HTTP GET, a TCP connection, a gRPC health check or a command. By default it runs every 10 seconds, times out after 1 second, and counts as failed after 3 failures in a row. Liveness decides whether the container should be restarted. Readiness decides whether it should get traffic. A failing readiness probe takes the Pod out of the Service's endpoints, and a passing one puts it back. A startup probe protects slow starters by holding off the other two probes until it passes. bag-api follows the usual split. /healthz answers while the process works, and /readyz also checks Postgres. In Lab 07, DATABASE_URL points at a database that does not exist yet. The Pod shows READY 0/1 with 0 restarts, because /readyz returns 503 while /healthz passes. Ask the class which probe a service with a slow cache warm-up needs. Source: Kubernetes Authors (2026), Liveness, Readiness and Startup Probes.

Requests and limits

containers:
- name: bag-api
  image: localhost:5000/bag-api:1.0
  resources:
    requests:
      cpu: 250m
      memory: 256Mi
    limits:
      cpu: "1"
      memory: 256Mi

The scheduler uses requests to choose a node. Through cgroups, a CPU limit slows the container down, and a memory limit kills it with exit code 137 and the reason OOMKilled (Kubernetes Authors, 2026).

Requests and limits connect the scheduler slide to the cgroups from Day 1. A request is what the scheduler reserves on a node. 250m means 250 millicores, a quarter of one CPU, and 256Mi is 256 mebibytes. A limit is the most the container may use, and the kubelet turns it into cgroup settings. CPU time can be shared out, so a container over its CPU limit is throttled and runs slower. Memory cannot be taken back, so a container over its memory limit is killed by the kernel's OOM killer. Kubernetes then reports the reason OOMKilled and exit code 137, as you saw with docker run --memory on Day 1. Some teams leave out the CPU limit to avoid throttling; that trades predictable performance for the use of idle CPU. ECS asks for similar numbers, cpu and memory, in the task definition. Ask the class what happens to a Pod that requests 20 CPUs on our 8-vCPU nodes. It stays Pending, and kubectl describe shows Insufficient cpu. Source: Kubernetes Authors (2026), Resource Management for Pods and Containers.

Quality of service classes

ClassWhen a Pod gets itWhen the node runs short of memory
GuaranteedEvery container sets CPU and memory limits, with requests equal to themEvicted last
BurstableAt least one container sets a request or a limitEvicted after all BestEffort Pods
BestEffortNo container sets any request or limitEvicted first

Kubernetes assigns the class from the resources you set. The bag-api settings on the previous slide give a Burstable Pod (Kubernetes Authors, 2026).

Kubernetes puts every Pod into one of three quality of service classes, based only on the requests and limits you set. You do not set the class yourself. When a node runs short of memory, the kubelet evicts Pods to protect the node. It evicts BestEffort Pods first, then Burstable Pods, and Guaranteed Pods last. To be Guaranteed, every container in the Pod needs CPU and memory limits, with requests equal to those limits. The class also sets the kernel's OOM score for the containers, so under pressure the kernel kills BestEffort processes first. A sensible default for services like bag-api and Postgres is to set requests that match their normal use, plus a memory limit. Avoid BestEffort Pods in shared clusters, because they are the first to go. The bag-api example is Burstable because its CPU request and CPU limit differ. Ask the class which class the scanner's Pods would get if its Deployment set no resources at all. Source: Kubernetes Authors (2026), Pod Quality of Service Classes.

Multi-container patterns

Burns and Oppenheimer (2016) named the sidecar, ambassador and adapter patterns. Init containers are the Kubernetes feature for setup steps that must finish first.

Burns and Oppenheimer, both co-authors of the Borg, Omega and Kubernetes paper, described patterns for containers that cooperate inside one Pod. A sidecar extends the main container, for example a log shipper that reads its log files, or a process that syncs files from Git. An ambassador stands between the app and other services. The app calls a local proxy on localhost, and the proxy knows how to reach a sharded cache or a database. An adapter turns the app's output into a standard format, for example metrics in the format that the monitoring system expects. Init containers are a Kubernetes feature. They run one after another, to completion, before the app containers start, so they suit waiting for a dependency or preparing files. The first three patterns make helpers reusable, because the same log shipper image can run beside any app. Ask the class which pattern a service mesh proxy such as Envoy follows. It is an ambassador, although meshes call it a sidecar. Sources: Burns and Oppenheimer (2016); Kubernetes Authors (2026), Init Containers.

Init containers and native sidecar containers

spec:
  initContainers:
  - name: wait-for-db
    image: public.ecr.aws/docker/library/busybox:1.37
    command: ["sh", "-c", "until nc -z bagtrack-db 5432; do sleep 2; done"]
  - name: log-shipper
    image: public.ecr.aws/docker/library/busybox:1.37
    restartPolicy: Always
    command: ["sh", "-c", "tail -F /logs/access.log"]
  containers:
  - name: bag-api
    image: localhost:5000/bag-api:1.0

Init containers run one after another and must finish before the app starts. An init container with restartPolicy: Always is a native sidecar, stable since Kubernetes 1.33 (Kubernetes Authors, 2026).

Here are both kinds in one Pod spec. wait-for-db is a classic init container. It uses busybox's nc to test the Postgres port, loops until the database answers, and exits. Lab 09 adds this init container to bag-api. Only after it exits does the kubelet start the next init container. log-shipper is listed under initContainers but has restartPolicy set to Always, which makes it a native sidecar. The kubelet starts it before bag-api, keeps it running for the whole life of the Pod, restarts it if it fails, and stops it after bag-api has stopped. Before this feature, a sidecar was a second regular container with no start order, and it kept Jobs from finishing, because a Job waits for every container to exit. The log-shipper is an example only, and the shared volume it reads is left out to keep the slide short. Ask the class what kubectl get pods shows for this Pod while the bagtrack-db Service does not exist yet. Source: Kubernetes Authors (2026), Init Containers and Sidecar Containers.

Three ways to use a ConfigMap

Variables are set once, when the container starts. Mounted files are updated after the ConfigMap changes (Kubernetes Authors, 2026).

A ConfigMap stores configuration that is not secret as name-value pairs, up to 1 MiB in total, so the same image can run in every environment. This is the twelve-factor rule from Day 1, which keeps configuration in the environment and out of the image (Wiggins, 2011). In the labs, the ConfigMap bag-api-config holds HUB and SEED. APP_VERSION stays out of it, because it is set as a build argument and describes the image itself. env with configMapKeyRef picks one entry and names the variable. envFrom turns every entry into a variable. A configMap volume writes every entry as a file, which suits whole files such as an nginx configuration. Variables are fixed when the container starts. Mounted files change after the kubelet's next sync, except when they are mounted with subPath, so kubectl rollout restart is the usual way to apply a change. ECS has no ConfigMap; a task definition holds environment variables or points to an environment file in S3. Ask the class why DATABASE_URL belongs in a Secret. Source: Kubernetes Authors (2026), ConfigMaps.

How Kubernetes stores and protects Secrets

  • Secret values are only base64-encoded, so anyone who can read a Secret can decode it
  • etcd holds Secrets unencrypted unless encryption at rest is turned on (Kubernetes Authors, 2026)
  • k3s turns encryption on with --secrets-encryption, and EKS encrypts all API data with AWS KMS by default (Amazon Web Services, 2026)
  • RBAC limits who can read Secrets, but anyone who can create a Pod in a namespace can mount its Secrets
  • External stores such as AWS Secrets Manager keep the value outside the cluster and mount it into Pods

Pods use Secrets in the same ways as ConfigMaps, as variables or as files.

A Secret is stored and used much like a ConfigMap, and Kubernetes adds only a few protections. In the labs, the Secret bag-api-db gives bag-api its DATABASE_URL, and the Secret bagtrack-db holds the Postgres password. The values in a manifest are only base64-encoded, and base64 -d reverses them. By default the API server writes Secrets to etcd unencrypted, so anyone with access to etcd or its backups can read them. k3s has the --secrets-encryption flag to turn on encryption at rest, and EKS encrypts all Kubernetes API data with AWS KMS by default from version 1.28. RBAC rules decide who may get or list Secrets. Because a Pod can mount any Secret in its namespace, permission to create Pods also gives access to Secrets. On EKS, the AWS Secrets and Configuration Provider for the Secrets Store CSI Driver mounts values from AWS Secrets Manager into Pods. ECS reads the same stores through the secrets field of a task definition. Sources: Kubernetes Authors (2026), Secrets; K3s Project Authors (2026); Amazon Web Services (2026).

Services and EndpointSlices

A Service gives a changing set of Pods one stable name, IP address and port. The EndpointSlice controller lists the Pods behind it, up to 100 per slice (Kubernetes Authors, 2026).

Pods come and go, and each new Pod gets a new IP address, so clients need something that stays the same. A Service gives them a stable name, a virtual IP address called the ClusterIP, and a port. Its selector decides which Pods belong to it. The EndpointSlice controller watches those Pods and writes their addresses and ports into EndpointSlice objects. Each slice has the label kubernetes.io/service-name=bag-api, so kubectl -n bagtrack get endpointslices -l kubernetes.io/service-name=bag-api finds them. Only ready endpoints get new traffic, which is how a failing readiness probe takes a Pod out of rotation. EndpointSlices replace the older Endpoints API, which kept every address of a Service in one object; slices of up to 100 endpoints keep each update small in large clusters. ECS does the same job with an ALB target group. The ECS service registers each task's IP address, and the target group's health check decides which tasks get traffic. Ask the class what kubectl get endpointslices shows for a Service whose selector has a typo. Source: Kubernetes Authors (2026), Service and EndpointSlices.

What kube-proxy programs

Nothing listens on the ClusterIP. The kernel sends each connection to one ready Pod (Kubernetes Authors, 2026).

kube-proxy is the reason a ClusterIP works even though no network interface owns that address. It runs on every node, watches Services and EndpointSlices, and turns them into packet-processing rules in the kernel. In the default iptables mode, a rule matches the ClusterIP and port, picks one ready endpoint at random, and rewrites the destination address. The nftables mode does the same with the newer nftables framework. The older IPVS mode has been deprecated since Kubernetes 1.35. The choice happens once per connection, so a client that keeps a connection open keeps talking to the same Pod, which matters for HTTP keep-alive. Every node has the same rules, so a client can reach a Pod on another node over the Pod network. Ask the class why ping 10.43.12.7 fails even when the Service works. The rules only cover TCP and UDP traffic to the Service's ports, so nothing answers ICMP. Source: Kubernetes Authors (2026), Virtual IPs and Service Proxies.

Internal and external access, and how EKS provides it

On EKS, the AWS Load Balancer Controller creates a Network Load Balancer for a LoadBalancer Service and an Application Load Balancer for an Ingress (Amazon Web Services, 2026).

Most Services handle traffic inside the cluster only, like bag-api for the board and the scanner. In your lab, the browser on the VM opens localhost:8081 for the board's LoadBalancer Service, or localhost:30080 for its NodePort. The k3d load balancer container forwards both ports to the nodes, where ServiceLB or the NodePort passes the traffic to the board Pods. On EKS, you install the AWS Load Balancer Controller. It watches Services of type LoadBalancer and creates a Network Load Balancer, and it watches Ingress objects and creates an Application Load Balancer for HTTP routing. With IP targets, the load balancer sends traffic to Pod IP addresses, which the VPC CNI makes routable; Fargate Pods support only IP targets. Without the controller, EKS falls back to a legacy cloud provider that creates Classic Load Balancers. Ingress and the newer Gateway API are outside this course. Ask the class which BagTrack Services need any external access at all. Source: Amazon Web Services (2026), Amazon EKS User Guide.

Deployments, ReplicaSets and Pods

You change the Deployment. It creates one ReplicaSet for each version of the Pod template, and each ReplicaSet keeps its number of Pods running (Kubernetes Authors, 2026).

A Deployment does not create Pods itself. It manages ReplicaSets, and each ReplicaSet keeps a set number of identical Pods running from one Pod template. When you change the template, for example the image tag, the Deployment creates a new ReplicaSet and moves Pods from the old one to the new one. The old ReplicaSet stays with zero Pods, so a rollback only has to scale it back up. The suffix in the names is a hash of the template, and every Pod has it as the pod-template-hash label. By default a Deployment keeps ten old ReplicaSets. You rarely create ReplicaSets yourself. The ECS equivalent is an ECS service and its deployments. The service keeps the desired count, and each deployment tracks the tasks of one task definition revision. Ask the class what happens if you delete the ReplicaSet that the Deployment uses now. The Deployment creates it again. Source: Kubernetes Authors (2026), Deployments.

Scaling a Deployment

# Run five copies of bag-api instead of three
kubectl -n bagtrack scale deployment/bag-api --replicas=5

# See which node each Pod runs on
kubectl -n bagtrack get pods -l app=bag-api -o wide

# Delete one Pod and watch its replacement start
kubectl -n bagtrack delete pod <name-of-a-bag-api-pod>
kubectl -n bagtrack get pods -l app=bag-api --watch

Scaling changes one number in the spec, and the ReplicaSet controller creates or deletes Pods to match. A HorizontalPodAutoscaler changes it from measured CPU or memory use (Kubernetes Authors, 2026).

Scaling a Deployment is a change to one field. kubectl scale writes spec.replicas, the ReplicaSet controller creates the extra Pods, the scheduler spreads them over the nodes, and the EndpointSlice controller adds them to the Service when they become ready. Deleting a Pod shows the same loop. The count drops below the spec, and a new Pod appears. Lab 08 also shows the limit of scaling. bag-api still keeps its bags in memory there, so each replica has its own data, and each refresh of the board can show a different hostname and different bags. Scaling works cleanly only when Pods keep no state, which is why Lab 09 moves the data into Postgres. A HorizontalPodAutoscaler changes replicas for you from metrics, and k3s includes the metrics-server it needs. On ECS the matching feature is Service Auto Scaling. Ask the class what happens at the next kubectl apply if the manifest in Git says 3 replicas and someone scaled to 5 by hand. Sources: Kubernetes Authors (2026), Deployments and Horizontal Pod Autoscaling; K3s Project Authors (2026).

Rolling update parameters

maxSurge sets how many extra Pods may exist during the update, and maxUnavailable sets how many may be missing. Both default to 25% of the replicas (Kubernetes Authors, 2026).

A rolling update replaces Pods a few at a time. maxSurge is how many Pods above the desired count may exist, and maxUnavailable is how many below it may be missing. Lab 08 runs three bag-api replicas with maxSurge 1 and maxUnavailable 0. The Deployment starts one new Pod, waits until its readiness probe passes, removes one old Pod, and repeats. This setting never drops below full capacity, at the cost of one extra Pod during the update. Both values default to 25%. Kubernetes rounds maxSurge up and maxUnavailable down, so for three replicas the defaults also come to 1 and 0. Without a readiness probe, a Pod counts as ready as soon as its container starts, and traffic can reach it before the app can answer. The other strategy, Recreate, stops all old Pods first, which suits apps that cannot run two versions at once. Ask the class what maxSurge 0 with maxUnavailable 0 would do. The API rejects it, because no Pod could ever be replaced. Source: Kubernetes Authors (2026), Deployments.

Rollout history and rollback

kubectl -n bagtrack set image deployment/bag-api bag-api=localhost:5000/bag-api:1.0.3
kubectl -n bagtrack rollout status deployment/bag-api

kubectl -n bagtrack rollout history deployment/bag-api
kubectl -n bagtrack rollout undo deployment/bag-api
kubectl -n bagtrack rollout undo deployment/bag-api --to-revision=1

A rollout that stops making progress is reported as ProgressDeadlineExceeded, after 600 seconds by default. Kubernetes takes no other action, so you or your deployment tool start the rollback (Kubernetes Authors, 2026).

Each change to the Pod template creates a new revision, and kubectl rollout history lists them. In a team you would change the manifest in Git and apply it instead of using kubectl set image, so that the change is reviewed. In Lab 08 you roll out the image that your Day 2 pipeline tagged with its build number, such as 1.0.3. Then you set the tag 9.9, which does not exist. The new Pod goes to ImagePullBackOff and never becomes ready, and because maxUnavailable is 0 the old Pods keep serving. After its deadline, the Deployment reports ProgressDeadlineExceeded and Kubernetes stops there. kubectl rollout undo scales the previous ReplicaSet back up. Headlamp has no screen for rollout history or undo, so this part stays in the terminal. The Harness platform, which United uses, has rollback for Kubernetes and ECS deployments, and ECS has a deployment circuit breaker that can roll back on its own. Ask the class what should trigger a rollback in their own services. Sources: Kubernetes Authors (2026), Deployments; Harness (2026); Amazon Web Services (2026).

Volumes in a Pod

Volume typeWhere the data isHow long it lastsTypical use
emptyDirThe node's disk, or memoryAs long as the PodScratch files, and files shared between containers
configMap, secretObjects in the APIAs long as the objectConfiguration files
hostPathA path on the nodeAs long as the nodeNode agents only
persistentVolumeClaimStorage outside the PodIndependent of any PodDatabases

hostPath exposes the node's filesystem to the Pod. The Baseline Pod Security Standard forbids it (Kubernetes Authors, 2026).

A volume is a directory that the containers of a Pod can mount. The Pod spec lists the volumes, and each container chooses where to mount them. emptyDir starts empty when the Pod is scheduled and is deleted with the Pod. It survives container restarts, which makes it the right place for files shared between containers, as the writer and reader containers do in Lab 09. hostPath mounts a path from the node itself. That is risky, because the Pod can read or change node files, and its data depends on which node it runs on. Node agents in DaemonSets are the usual exception. For data that must outlive the Pod, the Pod refers to a PersistentVolumeClaim, which is the next slide. Compared with Day 1, hostPath is the Kubernetes form of a bind mount, and a PersistentVolumeClaim plays the role of a named volume. Ask the class what happens to an emptyDir when the container restarts, and when the Pod is deleted. Source: Kubernetes Authors (2026), Volumes and Pod Security Standards.

PersistentVolumes and PersistentVolumeClaims

Kubernetes binds each claim to a matching volume. The volume and its data outlive the Pods that use it (Kubernetes Authors, 2026).

Persistent storage in Kubernetes separates two jobs. The app team writes a PersistentVolumeClaim, which says how much storage it needs and how it will be mounted. The cluster provides PersistentVolumes, which represent real storage such as a directory on a node, an NFS share or an Amazon EBS volume. Kubernetes binds each claim to one volume, and the Pod mounts the claim by name. This split means that a manifest asks for storage the same way on k3d and on EKS, while the storage behind it differs. A PersistentVolume has its own lifecycle. Deleting the Pod leaves the claim and the data in place, and a new Pod that mounts the same claim sees the same files. In Lab 09 you delete the Postgres Pod and check that the data you created is still there. Ask the class who should be allowed to create PersistentVolumes by hand in a shared cluster. Source: Kubernetes Authors (2026), Persistent Volumes.

StorageClasses and dynamic provisioning

k3s on your VMAmazon EKS
StorageClasslocal-path, the defaultOne that you define, such as gp3
ProvisionerLocal Path ProvisionerAmazon EBS CSI driver
Where the data isA directory under /var/lib/rancher/k3s/storage on one nodeAn EBS volume in one Availability Zone

A claim names a StorageClass. The class's provisioner creates a matching PersistentVolume on demand (K3s Project Authors, 2026; Amazon Web Services, 2026).

Creating PersistentVolumes by hand does not scale, so most clusters use dynamic provisioning. A StorageClass names a provisioner and its parameters, and a claim that names the class gets a new volume made for it. k3s ships the Local Path Provisioner with a default class called local-path. It creates a directory under /var/lib/rancher/k3s/storage on the node where the Pod runs, which in k3d is inside that node's container, and the Pod is then bound to that node. On EKS you install the Amazon EBS CSI driver as an add-on and define a class such as gp3, and each claim gets a new EBS volume. A gp3 volume belongs to one Availability Zone and attaches to one instance at a time, so the Pod must run in that zone. For storage that many Pods share, EKS uses Amazon EFS through its own CSI driver. Pods on EKS Fargate cannot mount EBS volumes. Ask the class what happens to a local-path volume if its k3d node container is deleted. Sources: K3s Project Authors (2026); Amazon Web Services (2026).

Access modes and reclaim policy

SettingValueMeaning
Access modeReadWriteOnceRead-write from one node at a time
ReadWriteOncePodRead-write from one Pod
ReadOnlyManyRead-only from many nodes
ReadWriteManyRead-write from many nodes, for example Amazon EFS
Reclaim policyDeleteDeleting the claim deletes the volume and its data
RetainThe volume and its data stay until an administrator removes them

Dynamically provisioned volumes take the reclaim policy of their StorageClass, which is Delete by default (Kubernetes Authors, 2026).

Access modes describe how a volume can be mounted, and the storage must support the mode you ask for. ReadWriteOnce means one node can mount it read-write. Several Pods on that node can still share it, which surprises people. ReadWriteOncePod limits it to one Pod, which is a safe choice for a database. EBS and local-path volumes support ReadWriteOnce, and Amazon EFS supports ReadWriteMany. The lab claims use local-path with ReadWriteOnce and the Delete policy. The reclaim policy decides what happens to the volume when its claim is deleted. Delete removes the volume and its data, and it is the default for dynamically provisioned volumes. Retain keeps them for an administrator to recover or clean up, which is what you want for production databases. Deleting a StatefulSet does not delete its claims either, which protects data from a mistaken delete. Ask the class which reclaim policy they would want for the Postgres volume in production, and what extra work it creates. Source: Kubernetes Authors (2026), Persistent Volumes.

StatefulSets

Each Pod keeps its name, DNS name and claim when it is replaced. Pods start one at a time in order and stop in reverse order (Kubernetes Authors, 2026).

A Deployment treats its Pods as interchangeable. They have random names and one shared template, and any Pod can replace any other. Databases need the opposite. A StatefulSet gives each Pod a fixed ordinal name, such as bagtrack-db-0, and recreates a deleted Pod with the same name. Through the headless Service named in serviceName, each Pod also gets a stable DNS name, so clients can reach a specific member. volumeClaimTemplates give each Pod its own claim, such as data-bagtrack-db-0, and a replacement Pod gets the same claim back. In Lab 09 you delete bagtrack-db-0 and find your data still there when the Pod returns. By default Pods start one at a time in order, each waiting for the previous one to be ready, and scale down in reverse order. A StatefulSet does not make Postgres replicate; that is the job of the database or an operator, which is why Lab 09 runs one replica. Ask the class what a StatefulSet adds for a single database Pod compared with a Deployment and a claim. Source: Kubernetes Authors (2026), StatefulSets.

How a Job runs Pods to completion

FieldMeaningDefault
completionsHow many Pods must succeed1
parallelismHow many Pods may run at once1
backoffLimitFailures allowed before the Job fails6
activeDeadlineSecondsTime limit for the whole JobNone
ttlSecondsAfterFinishedDeletes the finished Job after this many secondsNone

A Job's Pods use restartPolicy OnFailure or Never. The Job succeeds when enough Pods exit with code 0 (Kubernetes Authors, 2026).

Deployments are for processes that should run forever. A Job is for work that ends, such as a database migration, a report, or loading seed data. In Lab 09 the seed Job runs python -m bagtrack.seed once. The Job controller creates Pods until the number of successful completions is reached. If a Pod fails, the Job creates another, up to backoffLimit. The Pod template must use OnFailure, which restarts the container in the same Pod, or Never, which makes a new Pod for each retry and keeps the failed Pods for their logs. Finished Jobs and their Pods stay until you delete them, unless ttlSecondsAfterFinished cleans them up. That matters on EKS Fargate, where AWS notes that finished Pods still cost money. The exit codes from Day 1 matter here, because only 0 counts as success. ECS has no Job object; you run a standalone task, or schedule one with Amazon EventBridge. Ask the class which field stops a stuck Job from running forever. Sources: Kubernetes Authors (2026), Jobs; Amazon Web Services (2026).

CronJobs

apiVersion: batch/v1
kind: CronJob
metadata: {name: bag-report, namespace: bagtrack}
spec:
  schedule: "* * * * *"
  concurrencyPolicy: Forbid    # optional, not set in the lab
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report
            image: localhost:5000/scanner:1.0
            args: ["report"]

The CronJob controller creates a Job at each scheduled time. concurrencyPolicy decides what happens when the previous Job is still running (Kubernetes Authors, 2026).

A CronJob creates a Job on a schedule written in the standard cron format: minute, hour, day of month, month and day of week. This one runs every minute, as in Lab 09, and it starts the scanner in its report mode. concurrencyPolicy is Allow by default, which lets runs overlap. Forbid skips a run while the last one is still going, and Replace stops the old run and starts the new one. A report should not overlap with itself, so Forbid fits. The controller keeps the last three successful Jobs and the last failed one. Schedules use the time zone of the controller manager unless you set the timeZone field. If the cluster was down at a scheduled time, startingDeadlineSeconds limits how late a missed run may still start. The documentation asks for Jobs that are safe to run twice, because in rare cases a schedule creates two Jobs or none. Ask the class what would go wrong if the report job were not safe to run twice. Source: Kubernetes Authors (2026), CronJob.

DaemonSets

DaemonSets run node-level agents such as log collectors and network plugins. A node that joins the cluster gets the Pod automatically (Kubernetes Authors, 2026).

A DaemonSet runs one copy of a Pod on every node, or on every node that matches a selector. You use it for software that belongs to the node rather than to one application: log collectors that read container logs from the node's disk, metrics agents, storage drivers and network plugins. When a node joins, the DaemonSet controller adds a Pod there, and when a node leaves, its Pod goes with it. In your k3d cluster, ServiceLB is built on DaemonSets. On EKS, the VPC CNI's aws-node agent and kube-proxy run as DaemonSets. EKS Fargate does not support DaemonSets, because each Fargate Pod runs on its own isolated node; AWS suggests running the agent as a sidecar in each Pod instead. In Lab 09 you deploy a small node agent and see one Pod per node with kubectl get pods -o wide. Ask the class how many node-agent Pods there will be after a fourth node joins. Sources: Kubernetes Authors (2026), DaemonSet; Amazon Web Services (2026).

Scaling approaches compared

NeedDocker and ComposeAmazon ECSKubernetes
Run more copies--scale or deploy.replicas, on one hostThe service's desired countThe Deployment's replicas
Scale automaticallyNot built inService Auto ScalingHorizontalPodAutoscaler
Spread the loadDNS round robin on the networkAn ALB target groupA Service and kube-proxy
Add capacityA bigger hostFargate, or more EC2 instancesMore nodes, or Fargate on EKS

Every platform scales a stateless service by adding copies behind one address. Stateful parts such as Postgres need a different plan (Amazon Web Services, 2026; Kubernetes Authors, 2026).

This slide and the next one serve the course objective of evaluating approaches to scaling, resilience and microservice design. All three platforms scale a stateless service the same way. They run more copies and put one address in front of them. Docker and Compose do it on one host, so they cannot add capacity beyond that machine. ECS and Kubernetes both keep a desired count and can change it automatically, ECS through Service Auto Scaling and Kubernetes through the HorizontalPodAutoscaler. On Fargate, AWS supplies the capacity for new copies; clusters built on EC2 instances also need node scaling. BagTrack shows the design side. In Lab 08, with in-memory storage, each bag-api replica had its own bags. Once the data moved to Postgres in Lab 09, bag-api could scale out, and the board is static files. The twelve-factor rules on processes and disposability describe this design (Wiggins, 2011). Resilience approaches compared

NeedDocker and ComposeAmazon ECSKubernetes
Restart a failed containerA restart policyThe service replaces the taskThe kubelet restarts it, and the ReplicaSet replaces lost Pods
Detect an unhealthy appHEALTHCHECK and depends_on conditionsContainer and target group health checksLiveness, readiness and startup probes
Survive a host or zone failureNot possible on one hostTasks spread across Availability ZonesNew Pods on other nodes and zones
Undo a bad releaseBy handDeployment circuit breaker with rollbackkubectl rollout undo, or a CD tool

ECS and Kubernetes replace failed copies on other hosts. Docker and Compose cannot, because each manages one host (Amazon Web Services, 2026; Kubernetes Authors, 2026).

Resilience is about what happens when something fails. On one Docker host, restart policies bring a crashed container back, but nothing helps when the host itself fails. ECS and Kubernetes replace failed copies on other machines, and they use health checks to decide what has failed. ECS uses container health checks and the load balancer's target group checks, and Kubernetes uses probes. For host and zone failures, ECS with Fargate spreads a service's tasks across Availability Zones on a best-effort basis. Kubernetes reaches the same result with nodes in several zones and topology spread constraints. For bad releases, the ECS deployment circuit breaker can roll back automatically, while Kubernetes reports a stuck rollout and leaves the rollback to you or to a CD tool such as Harness. The app's design also affects resilience. It helps to have readiness that checks dependencies, liveness that does not, and a clean shutdown on SIGTERM. Ask the class which BagTrack failure would hurt most, and which row protects against it. Sources: Amazon Web Services (2026); Kubernetes Authors (2026).
