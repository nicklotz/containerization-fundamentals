Monolithic and microservice architectures

A monolith is built and deployed as one unit. Lewis and Fowler (2014) describe microservices as “a suite of small services, each running in its own process and communicating with lightweight mechanisms”.

Start with the monolith, because most systems begin as one. In a monolith the modules call each other as functions inside one process and share one database. A change to any module means building and deploying the whole application. Lewis and Fowler's 2014 article named the microservice style. The term was discussed at a workshop of software architects near Venice in May 2011, and the same group settled on "microservices" in May 2012. Newman (2021) defines microservices as independently releasable services that are modeled around a business domain. BagTrack is a small example. bag-api, the scanner and the board are separate programs in Python, Go and JavaScript, each with its own image and its own deployment. Ask: is your team's main application one deployable unit or several? Sources: Lewis, J., and Fowler, M. (2014). Microservices. martinfowler.com. Newman, S. (2021). Building Microservices (2nd ed.). O'Reilly.

Trade-offs between monoliths and microservices

ConcernMonolithMicroservices
DeploymentThe whole application at onceEach service on its own schedule
ScalingCopies of the whole applicationOnly the services that need more capacity
FailureFunction calls inside one processNetwork calls that can be slow or fail
DataOne database with local transactionsEach service owns its data, and consistency across services needs design
OperationsOne application to run and monitorMany services to deploy, trace and secure

Newman (2021) recommends microservices for a specific goal, such as independent deployment, because they add cost in operations, testing and data consistency.

Read the table row by row and give an example for each row. Deployment: with a monolith, a one-line change to reports waits for the next release of everything. Scaling: if scanning load doubles, a monolith scales every module together, while microservices scale only the scanning service. Failure: a function call does not time out, but a network call can, so every caller needs timeouts and retries. Lewis and Fowler call this "design for failure". Data: once each service owns its tables, a business transaction across two services cannot use one database transaction. Newman also warns about the "distributed monolith", a set of services that must still be deployed together. It has the costs of both styles. Ask: which row matters most for your team today? Sources: Newman, S. (2021). Building Microservices (2nd ed.). Lewis, J., and Fowler, M. (2014). Microservices.

Stateless services and horizontal scaling

A stateless service keeps no client data in memory or on local disk between requests (Wiggins, 2011). Any instance can answer any request, so you add instances to handle more load.

There are two ways to handle more load. Vertical scaling gives one instance a bigger machine. It has an upper limit and usually needs a restart. Horizontal scaling adds more instances behind a load balancer, which twelve-factor calls scaling out through the process model. It works only if the instances are interchangeable, so none of them may keep data that a later request needs. Sticky sessions send a user back to the same instance. They are a workaround that breaks when that instance stops. BagTrack shows this on Day 3. You scale bag-api to several replicas, and the board's footer, which comes from /api/info, shows a different hostname as requests are spread out. Ask: what does your service keep in memory between requests today, such as sessions or caches? Source: Wiggins, A. (2011). The Twelve-Factor App, factors VI (Processes) and VIII (Concurrency). 12factor.net.

State belongs in backing services

Twelve-factor treats a database, queue or cache as a backing service, an attached resource that the app finds through a URL in its config (Wiggins, 2011). Changing the URL switches the database without changing the code.

A container's own filesystem is temporary. When the container is removed, its writable layer is removed with it. Anything that must outlive one instance goes to a backing service. Wiggins lists datastores, message queues, mail services and caches as examples. He says a deploy should be able to swap a local database for a managed one, such as Amazon RDS, by changing only the resource handle in the config. For BagTrack that handle is DATABASE_URL. In Lab 03 it points to a Postgres container on your VM. In AWS the same image could point to a managed database. bag-api can also keep bags in memory. Ask: what happens if two bag-api replicas run in memory mode? Each one has its own list of bags, and the board shows different data depending on which replica answers. Source: Wiggins, A. (2011). The Twelve-Factor App, factor IV (Backing services).

Configuration comes from the environment

  • Config is everything that varies between deploys, such as database URLs, credentials and hostnames (Wiggins, 2011)
  • The application reads it from environment variables when it starts
  • The same image runs in development, test and production
  • Secrets are injected at run time and are never built into the image

ECS task definitions, Compose files and Kubernetes Pods all set environment variables for a container.

Twelve-factor's third factor says to store config in the environment. Config here means the values that change between deploys: resource handles, credentials and hostnames. It does not include internal settings such as URL routes, which stay in the code. Wiggins gives a test for this. Could you publish the code as open source right now without leaking a credential? If you could, config is separate from code. Environment variables work with every language and every orchestrator. In Lab 03 you pass DATABASE_URL to bag-api with docker run -e. On Day 2 you set it in Compose and in an ECS task definition, where secrets come from Secrets Manager or SSM Parameter Store. On Day 3 it comes from a ConfigMap and a Secret. Ask: where does your application read its database password from today? Source: Wiggins, A. (2011). The Twelve-Factor App, factor III (Config).

Disposable processes start fast and stop cleanly

  • Start in a few seconds, so new instances can take traffic soon after a scale-out
  • On SIGTERM, stop accepting new requests, finish the current ones, then exit
  • A worker returns its current job to the queue before it exits
  • Expect to be stopped at any time, by a deploy, a scale-in or host maintenance

Wiggins (2011) calls processes that can be started or stopped at a moment's notice disposable. Docker, ECS and Kubernetes all send SIGTERM first and SIGKILL after a grace period.

Factor IX says processes should be disposable. Fast startup matters because orchestrators replace instances all the time, during deploys, scaling and host maintenance. Graceful shutdown matters because the orchestrator sends SIGTERM first, waits for a grace period, and then sends SIGKILL, which a process cannot catch. Docker waits 10 seconds by default. ECS and Kubernetes wait 30 seconds by default. A web process should stop accepting connections, finish the requests in flight and exit. A worker, such as BagTrack's scanner, should finish or hand back its current job. In Lab 01 you see exit code 143 for a process that ended on SIGTERM and 137 for one that was killed. Ask: how long does your service take to start, and what happens to requests in flight during a deploy? Sources: Wiggins (2011), factors VI and IX; Docker documentation, docker container stop; Amazon ECS Developer Guide.

The CNCF definition of cloud native

  • Practices to develop, build and deploy workloads in public, private and hybrid clouds, at scale and in a programmatic, repeatable way
  • Loosely coupled systems that are secure, resilient, manageable, sustainable and observable
  • Usually built from containers, service meshes, multi-tenancy, microservices, immutable infrastructure, serverless and declarative APIs
  • Automation that allows frequent, predictable, high-impact changes with minimal toil

Version 1.1 replaced the 2018 text in 2024 and added multi-tenancy, serverless, security and sustainability (CNCF TOC, 2018, 2024).

The Cloud Native Computing Foundation was founded in 2015 under the Linux Foundation, and Kubernetes became its first hosted project. Its Technical Oversight Committee approved the first definition of cloud native on 11 June 2018 and version 1.1 on 26 February 2024. Read the definition as a list of properties. Containers are one item in the list, next to microservices, immutable infrastructure and declarative APIs. Immutable infrastructure means you replace a server or a container instead of changing it in place. A declarative API means you describe the state you want, such as three replicas, and a controller works to reach it. BagTrack uses several of these. It is a set of small services, it ships as images that do not change, and on Days 2 and 3 you describe it in Compose and Kubernetes files. Ask: which items on this list does your team already use? Source: CNCF Technical Oversight Committee (2018, 2024), CNCF Cloud Native Definition v1.0 and v1.1.

How virtual machines and containers share a host

A virtual machine runs its own kernel on virtual hardware that the hypervisor provides. Containers are processes that share the host's kernel, isolated by namespaces and limited by cgroups.

Draw the two stacks and compare them layer by layer. A hypervisor gives each virtual machine virtual hardware, and each machine boots its own kernel. A container has no kernel of its own. Its processes make system calls to the host kernel, which isolates and limits them. Your lab machine is itself a virtual machine on EC2, so the containers you start today run inside a VM, which is the usual arrangement in the cloud. On ECS with the EC2 launch type, many tasks share each instance's kernel. With Fargate, AWS runs each task in an isolated virtual environment that does not share CPU, memory, storage or network interfaces with other tasks. Ask: your containers run inside your Ubuntu VM, so whose kernel do they use? They use the VM's Ubuntu kernel. Sources: Felter et al. (2015); Amazon ECS Developer Guide, Fargate security considerations.

Felter et al. (2015) found that containers performed as well as or better than KVM virtual machines in almost all of their tests. AWS Fargate runs each task in its own isolated virtual environment (Amazon Web Services, n.d.).

Go through the rows. The main difference is the kernel. Containers start a process instead of booting an operating system, so they start quickly, and their images hold only what the application needs. The cost is a weaker boundary. All containers on a host share one kernel, so a kernel vulnerability or a badly configured container can affect its neighbours. That is why some platforms, Fargate among them, put a virtual machine boundary around each task. Felter and colleagues at IBM Research compared Docker and KVM with bare metal for CPU, memory, storage and network workloads. Both needed tuning for I/O-heavy workloads, and Docker's NAT networking added overhead. Ask: which workloads would you still run in a virtual machine? Examples are another operating system, a custom kernel module, or strong isolation between customers. Sources: Felter, W., et al. (2015), IEEE ISPASS; Amazon ECS Developer Guide, Fargate security considerations.

A short history of Linux containers

YearDevelopment
1979chroot in Version 7 Unix gives a process its own root directory
2000FreeBSD jails isolate processes, users and network addresses
2002Linux 2.4.19 adds the first namespace type, for mount points
2008Linux 2.6.24 adds control groups, and LXC combines them with namespaces
2013Docker adds a portable image format and a simple command line (Merkel, 2014)
2015Docker, CoreOS and others found the Open Container Initiative

Docker used kernel features that already existed and made them easy to use, with images that run the same way on any Linux host.

The ideas behind containers are older than Docker. chroot, added to Unix in 1979, changes the root directory that a process sees. FreeBSD jails extended the idea in 2000. Linux built the same isolation from smaller parts. Namespaces started with mount namespaces in 2002. Control groups came from Google engineers and were merged in Linux 2.6.24 in 2008. LXC combined the two into system containers. dotCloud released Docker in 2013. Docker first ran containers through LXC and replaced it with its own libcontainer library in 2014. Merkel's 2014 article describes what was new: an image format and tooling that start a container the same way on a laptop and on a server. In 2015 Docker gave libcontainer, as runc, to the new Open Container Initiative. Ask: has anyone used chroot or LXC? Sources: Kerrisk, namespaces(7) and cgroups(7); Merkel (2014), Linux Journal; Open Container Initiative.

Image, container, registry and runtime

TermMeaningExample
ImageA read-only package of filesystem layers and settings, such as the start commandpostgres:17

RegistryA server that stores images and serves them over HTTPAmazon ECR, localhost:5000

One image can start many containers, in the same way one program file can start many processes.

These four words come up in every lab, so define them carefully. An image is a set of files and settings. Nothing in it runs until a runtime starts it. A container is what you get when a runtime starts an image: one or more processes plus a writable layer. Removing a container does not remove its image. A registry is a server with an HTTP API for storing and fetching images, organised into repositories and tags. The word runtime has two meanings. A low-level runtime, such as runc or crun, implements the OCI Runtime Specification and starts the process. A high-level runtime, such as containerd or CRI-O, pulls images, manages storage and calls the low-level runtime. Ask: if you delete a container, is its image gone? It is not, and docker image ls still lists it. Source: Open Container Initiative (2024), Image Format, Runtime and Distribution specifications.

Because Docker, Podman, containerd and CRI-O all follow these specifications, an image you build on your VM runs under any of them (Open Container Initiative, 2024).

The Open Container Initiative was set up in June 2015 under the Linux Foundation by Docker, CoreOS and others, so that no single company owned the container format. Docker gave it its image format and runc. Version 1.0 of the image and runtime specifications came out in 2017. The 1.1 releases in 2024 added a standard way to attach artifacts, such as signatures and SBOMs, to an image, and you meet those on Day 2. The image specification describes what a builder produces. The distribution specification is the HTTP API that registries implement. Example: the bag-api image you build with Docker runs unchanged under containerd on your k3d cluster in Lab 07. How Docker runs a container

The runc process exits after it starts the container process, and the shim stays as the parent of the container process. Docker 29 also keeps images in containerd's image store by default.

Follow one docker run through the diagram. The CLI sends a REST request to dockerd over the Unix socket /var/run/docker.sock. dockerd resolves the image, sets up networks and volumes, and asks containerd over gRPC to create the container. In Docker 29 the images are stored in containerd's image store. containerd starts one shim process per container. The shim calls runc with an OCI bundle. runc creates the namespaces and cgroups, starts your process and exits. The shim keeps the process's output and exit code, which lets containerd restart without stopping containers. Kubernetes nodes, including k3s and Amazon EKS nodes, do not use dockerd. The kubelet calls containerd through the Container Runtime Interface. Anyone who can write to docker.sock controls dockerd, which runs as root, and Day 2 returns to this. Ask: which process will be the parent of your container in Lab 01? Sources: Docker documentation; Kubernetes documentation, Container runtimes.

A container is a process on the host

docker inspect --format '{{.State.Pid}}' web prints the host PID of a container's main process. The kernel isolates this process with namespaces and limits its resources with cgroups.

This is the central idea of the day. The Linux kernel has no object called a container. A container is an ordinary process that starts with its own set of namespaces and is placed in its own cgroup. From the host, ps shows the nginx process like any other process, with a host PID. Inside the container, the PID namespace gives the same process PID 1, and it sees no other processes. The PIDs on the slide are examples, and yours will differ. In Lab 01 you find the host PID of a container and compare its namespaces with the host's. Ask: if you run sudo kill -9 on that host PID, what happens to the container? It stops, and docker ps -a shows exit code 137. Sources: Kerrisk, namespaces(7) and pid_namespaces(7); Docker documentation, docker inspect.

A namespace wraps a global resource so that the processes inside see their own isolated instance of it (Kerrisk, n.d., namespaces(7)).

Each row is one namespace type from the namespaces(7) manual page. Docker creates a new namespace of each type for a container. The exception is user, which stays off unless the daemon uses user namespace remapping or runs rootless. Each process's namespaces appear as links under /proc/PID/ns. Two processes in the same namespace show the same inode number, which is how you check whether they share it. Namespaces can be shared on purpose. docker run --network container:web puts a second container into web's network namespace, so the two talk over localhost. A Kubernetes Pod works this way, and so does an ECS task on Fargate, where the containers in one task share a network namespace. Linux 5.6 added a time namespace, which Docker does not create by default. Ask: which namespace must two containers share to reach each other on localhost? Source: Kerrisk, M., namespaces(7), man7.org.

Control groups limit resources

Resourcedocker run flagcgroup v2 fileAt the limit
Memory--memory 64mmemory.maxThe kernel reclaims memory, then the OOM killer ends a process
CPU--cpus 0.5cpu.maxThe process is throttled and runs slower
Processes--pids-limit 100pids.maxNew processes and threads fail to start

Ubuntu 24.04 uses cgroup v2, with one unified hierarchy under /sys/fs/cgroup (Kerrisk, n.d., cgroups(7)). Without these flags a container has no limits and can use as much as the host allows (Docker, n.d.).

Namespaces decide what a process can see. Control groups decide how much CPU, memory and other resources it can use. The kernel arranges processes in a tree of groups and applies limits to each group through files. Version 1 had a separate tree for each controller. Version 2, stable since Linux 4.5, has one tree, which makes limits easier to follow. Docker turns each flag into a write to a file in the container's cgroup. For example, --cpus 0.5 becomes "50000 100000" in cpu.max, which means 50 ms of CPU time in every 100 ms period. In Lab 01, --memory 64m shows up as 67108864 in memory.max, which is 64 MiB in bytes. A CPU limit never kills a process. It only slows the process down. A memory limit is a hard ceiling. ECS task definitions and Kubernetes resource limits end up as the same cgroup settings. Ask: which limit would you set first for a service with a memory leak? Sources: Kerrisk, cgroups(7); Docker documentation, Resource constraints.

What happens when a container runs out of memory

The OOM killer chooses only among the processes in the container's cgroup, so the host and other containers keep running. If it kills the main process, the container stops with exit code 137, which is 128 plus 9 for SIGKILL.

When a container reaches memory.max, the kernel first tries to reclaim memory, for example by dropping file cache. If that fails, the OOM killer picks a process inside that cgroup and sends it SIGKILL, which a process cannot catch or handle. If the victim is the main process, the container exits with 137, and docker inspect shows OOMKilled as true. If the victim is a child process, such as one worker of a multi-process server, the container keeps running with one worker fewer, which is harder to notice. In Lab 01 you start a container with a small memory limit and a program that keeps allocating, then read the result. Kubernetes reports the same event as OOMKilled in the Pod's status. Ask: does exit code 137 always mean out of memory? It does not. docker kill and the stop timeout also give 137, so check OOMKilled. Sources: Kerrisk, cgroups(7); Docker documentation, Resource constraints.

How overlayfs builds a container's filesystem

When a process first changes a file from an image layer, overlayfs copies the whole file into the container layer and changes the copy (Docker, n.d.). docker diff lists the files a container has added (A), changed (C) or deleted (D).

overlayfs is a union filesystem in the Linux kernel since 3.18, and Docker 29 uses it through containerd's overlayfs snapshotter. It stacks read-only lower directories, the image layers, under one writable upper directory and presents the merged result as the container's root. The first write to a file from a lower layer copies the whole file up, which is called copy-on-write. Deleting a lower file creates a whiteout entry in the upper layer that hides it. The image layers never change, so a hundred containers from one image share one copy on disk and in the page cache. The container layer is removed with the container, and copying up large files is slow, so databases write to volumes instead. In Lab 02, docker diff shows the container layer, and you see why docker commit is not a repeatable build. Ask: a container appends one line to a 1 GB file from its image, so how much disk does it use? Source: Docker documentation, Storage drivers and OverlayFS.

Capabilities and seccomp

Capabilities

  • Linux splits root's privileges into about 40 capabilities (Kerrisk, n.d., capabilities(7))
  • Docker keeps 14 by default, such as CHOWN and NET_BIND_SERVICE
  • --cap-drop ALL removes them, and --cap-add adds one back

Seccomp

  • A filter on the system calls a process can make
  • Docker's default profile blocks about 44 of more than 300 system calls (Docker, n.d.)
  • Blocked calls include reboot, bpf and keyctl

Both restrictions also apply to root inside the container.

A Unix process used to be either root, with every privilege, or not. Since Linux 2.2 the kernel splits root's power into capabilities. CAP_NET_BIND_SERVICE allows binding to ports below 1024, and CAP_SYS_ADMIN allows mounts and many other operations. Docker starts containers with 14 capabilities, so root in a container has less power than root on the host. Seccomp is a second, independent filter. Docker's default profile blocks system calls that are not namespaced or that are risky, such as keyctl, reboot and loading BPF programs. --privileged turns most of these protections off, so treat it as host access. AWS Fargate restricts capabilities further. You cannot add CAP_SYS_ADMIN or CAP_NET_ADMIN there, and CAP_SYS_PTRACE is the one you can add. On Day 2, Lab 04 runs a container as non-root with capabilities dropped. Ask: which capability does a web server need to listen on port 80? Sources: Kerrisk, capabilities(7); Docker documentation, Seccomp security profiles; Amazon ECS Developer Guide, Fargate security considerations.

# Its cgroup and its memory limit
cat /proc/$PID/cgroup
cat /sys/fs/cgroup/system.slice/docker-$CID.scope/memory.max

# Run the host's ip tool inside its network namespace
sudo nsenter --target "$PID" --net ip addr

The /proc entries and nsenter work the same way for containers that containerd starts on a Kubernetes node.

Run these on a live container while the class watches, or point to the lab. docker inspect returns the container's full configuration and state, and --format picks one field with a Go template. ps shows the process and its parent, which is the shim. The ns directory lists one link per namespace type. Compare the inode numbers with /proc/self/ns to see which ones differ from the host. /proc/PID/cgroup prints the cgroup path. On Ubuntu 24.04 Docker uses the systemd cgroup driver, so the path is system.slice/docker-ID.scope. nsenter enters one or more namespaces of a target process and runs a host program there. This helps when the image has no shell or tools. lsns and docker top give two more views. Ask: why does ls on /proc/$PID/ns need sudo? The process belongs to root. Sources: Kerrisk, namespaces(7) and cgroups(7); util-linux, nsenter(1).

Reading container exit codes

CodeMeaningCommon cause
0The main process exited successfullyA one-off task finished
1The application reported an errorAn unhandled exception
125Docker could not run the containerAn unknown flag, or a name already in use
126The command exists but cannot runThe file is not executable
127The command was not foundA typo in CMD, or a missing binary
137Killed by SIGKILL (128 + 9)The OOM killer, docker kill, or the stop timeout
143Ended by SIGTERM (128 + 15)docker stop, when the process exits on the signal

Docker returns 125, 126 and 127 itself, and every other code is the exit status of the container's command (Docker, n.d.).

Exit codes are the first clue when a container stops. docker run reserves 125, 126 and 127 for its own failures, as the Docker reference describes. Codes above 128 follow the shell convention of 128 plus the signal number. 137 is SIGKILL, which is signal 9, and 143 is SIGTERM, which is signal 15. Code 1 is whatever the application chose to mean failure. A container that exits with 0 under the restart policy always is restarted anyway. In Lab 01 you produce several of these codes on purpose and read them with docker ps -a and docker inspect. ECS shows the same code in the stopped task's container details, and Kubernetes shows it as the last state of the container. Ask: a container exits with 137 and OOMKilled is false, so what else could have killed it? Source: Docker documentation, docker run reference, Exit status.

How an image is stored

Every part is stored and requested by the SHA-256 digest of its content, which is called content-addressable storage (Open Container Initiative, 2024). Images that share a base layer store and download that layer once.

Walk from left to right. A tag such as python:3.13-slim usually points to an image index, which lists one manifest per platform, for example linux/amd64 and linux/arm64. Docker picks the manifest for your machine. The manifest lists a config and the layers, each by media type, size and digest. The config holds the settings from the Dockerfile, such as the entrypoint, environment, user and working directory, plus the build history. Each layer is a compressed tar archive of file changes. Every object is named by the hash of its content. A host or a registry can therefore check whether it already has a layer before downloading it, and a single changed byte gives a different name. In Lab 02 you inspect a base image's layers with docker image inspect and docker history. Ask: two images are built FROM the same base, so how much disk does the base use? Source: Open Container Initiative (2024), OCI Image Format Specification v1.1.

The main Dockerfile instructions

InstructionWhat it does
FROMSets the base image for this build stage
WORKDIRSets the working directory for later instructions and for the container
COPYCopies files from the build context into the image
RUNRuns a command during the build and saves the result as a layer
ENVSets an environment variable in the image
USERSets the user that later instructions and the container run as
EXPOSEDocuments the port the application listens on
CMD, ENTRYPOINTSet the command that runs when the container starts

Only RUN, COPY and ADD create filesystem layers. The other instructions change the image configuration, and docker history shows them as 0 B steps.

These eight instructions cover most Dockerfiles, and you use them in Lab 02. FROM starts each stage. WORKDIR creates the directory if it does not exist, which is cleaner than RUN cd. Prefer COPY over ADD. ADD can also fetch URLs and unpack archives, which makes a build harder to predict. Each RUN creates a layer, so join commands that belong together, such as apt-get update and apt-get install, in one RUN. EXPOSE does not publish anything. It records the port for people and for tools. CMD gives a default command that docker run arguments replace. ENTRYPOINT fixes the program, and CMD then supplies its default arguments. Other instructions you will meet are ARG, LABEL, HEALTHCHECK and STOPSIGNAL. Ask: which instruction would you change to move bag-api to a newer Python release? Source: Docker documentation, Dockerfile reference and Building best practices.

How the build cache works

FROM public.ecr.aws/docker/library/python:3.13-slim
WORKDIR /app

# Dependencies change rarely, so they are installed first
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Source code changes often, so it is copied last
COPY . .
CMD ["uvicorn", "bagtrack.main:app", "--host", "0.0.0.0", "--port", "8000"]

Docker reuses a cached layer while the instruction and the files it copies are unchanged. Once a layer changes, every layer after it is rebuilt, so put the instructions that change least near the top (Docker, n.d.).

Walk through two edits. If you change a Python file, the cache holds up to the pip install layer, and only the last COPY and the layers after it run again, so the rebuild is fast. If you change requirements.txt, pip install runs again too. If you put COPY . . before pip install, every code change reinstalls all dependencies. For COPY, the cache compares the contents of the copied files. For RUN, it compares only the command text. RUN apt-get update therefore stays cached even after the package index on the internet has changed. Join it with the install command, or build with --no-cache when you need fresh packages. Day 2 adds cache mounts, which keep pip's download cache between builds. Ask: what happens to the cache if you add a comment at the end of bagtrack/main.py? Source: Docker documentation, Docker build cache.

The build context and .dockerignore

# .dockerignore
.git
.venv/
__pycache__/
*.pyc
.pytest_cache/
.env

docker build sends the build context, the folder you name, to the builder without the paths that .dockerignore lists. Leaving out .git, virtual environments and .env files makes the context smaller and keeps secrets out of the image.

In docker build -t bag-api:1.0 . the final dot is the build context. Everything in that folder is sent to BuildKit, and COPY can only see files inside it. The .dockerignore file in the root of the context excludes paths before they are sent. Patterns follow the Go filepath.Match rules, ** matches any number of directories, and a line that starts with ! adds an exception. Without the file, COPY . . copies your .git history and your local virtual environment into the image, and any edit there invalidates the cache. A .env file with a real password would end up in a layer. Removing it in a later RUN does not help, because the earlier layer still contains it and anyone with the image can extract it. Ask: a secret is copied in one layer and deleted in the next, so is it in the image? Source: Docker documentation, Build context and .dockerignore files.

Exec form, shell form and PID 1

Exec form

CMD ["uvicorn", "bagtrack.main:app", "--host", "0.0.0.0"]
  • Docker starts uvicorn with no shell
  • uvicorn is PID 1 and receives the SIGTERM from docker stop
  • Works in images without a shell

Shell form

CMD uvicorn bagtrack.main:app --host 0.0.0.0
  • Docker wraps the command in /bin/sh -c
  • The shell may stay as PID 1 and not pass SIGTERM on (Docker, n.d.)
  • Needs /bin/sh in the image

A process running as PID 1 receives SIGTERM only if it installs a handler for it (Kerrisk, n.d., pid_namespaces(7)).

Both forms set the same command, and they start it differently. The exec form is a JSON array. Docker runs the program itself, so it becomes PID 1 and receives the SIGTERM that docker stop sends. The shell form wraps the command in /bin/sh -c. Docker's documentation warns that the shell then stays as PID 1 and does not pass signals on. The application is killed with SIGKILL after the 10-second timeout and exits with 137. dash, the /bin/sh on Debian-based images, replaces itself with a single simple command, so the problem does not always appear, and you should not rely on that. There is a second issue. The kernel does not apply default signal actions to PID 1, so a plain Python script as PID 1 ignores SIGTERM unless it installs a handler. uvicorn and gunicorn install one. docker run --init adds a small init process that forwards signals. Sources: Docker documentation, Dockerfile reference; Kerrisk, pid_namespaces(7).

Tags and digests

A tag is a name that the next push can move to a different manifest. A digest is the SHA-256 hash of the manifest, so it always refers to the same content (Open Container Initiative, 2024).

A tag is a pointer in the registry, and pushing a new build with the same tag moves the pointer. latest is only the default tag name and says nothing about age. Two hosts that pull bag-api:1.0 an hour apart can get different images. That causes trouble when an orchestrator starts new tasks or Pods during scaling. A digest names the content itself, so pulling by digest gives the same bytes every time. Amazon ECR can make a repository's tags immutable. A push that reuses a tag then fails with ImageTagAlreadyExistsException. In Lab 02 you push bag-api to the local registry, read its digest and pull it back by digest. Day 2 builds a tagging strategy on this. Ask: if production runs bag-api:1.0, how would you find out which build that is? Sources: Open Container Initiative (2024), Image Format Specification; Amazon ECR User Guide, Image tag mutability.

Consume, extend or build a custom image

ApproachWhat you doBagTrack example
ConsumeRun a published image as it is, configured at run timedb runs postgres:17 with a volume and environment variables
ExtendStart FROM an application image and add your files or settingsboard adds its HTML and JavaScript to an unprivileged nginx image
CustomStart FROM a language or minimal base and build your own applicationbag-api starts FROM python, and on Day 2 the scanner starts FROM scratch

With a custom image you control every layer, and you must also apply base image updates and security patches yourself.

Most systems use all three approaches. Consuming an image means you trust its publisher for updates and fixes. Prefer Docker Official Images, Verified Publisher images, or images that your platform team approves. You configure a consumed image only through environment variables, mounts and commands, as you do for Postgres in Lab 03. Extending an image keeps the publisher's runtime and adds your content. The board inherits nginx's configuration and its non-root user. A custom image gives you full control over every layer and makes you responsible for all of them. Rebuild custom and extended images when the base image gets security fixes, or they stay vulnerable. Day 2 adds scanning, which tells you when a rebuild is needed. Ask: which approach does your team use for its main service, and who updates the base image? Source: Docker documentation, Docker Official Images and Building best practices.

Pushing and pulling images

# The registry host is the first part of the name
docker tag bag-api:1.0 localhost:5000/bag-api:1.0

# Upload the layers the registry lacks, then the manifest
docker push localhost:5000/bag-api:1.0

# List the tags in a repository (OCI Distribution API)
curl http://localhost:5000/v2/bag-api/tags/list

# Download the manifest by tag, then any missing layers
docker pull localhost:5000/bag-api:1.0

A name without a registry host, such as python:3.13-slim, refers to Docker Hub. For Amazon ECR you run docker login with a token from the AWS CLI before you push (Amazon Web Services, n.d.).

docker tag adds a second name to the same image, and nothing is copied. The registry host in the name tells docker push where to send it. Push first checks which layers the registry already has, uploads the rest, and finally uploads the manifest under the tag. That is why a second push of a slightly changed image prints "Layer already exists" for most layers. Pull works the other way. It fetches the manifest for the tag and then downloads only the layers that are missing locally. The curl call uses the OCI Distribution API, which every registry implements. Docker allows plain HTTP for registries on localhost, so the lab registry needs no TLS. For ECR, aws ecr get-login-password produces a token for docker login. In the Harness platform, a connector holds those credentials, and the Build and Push to ECR step uses them. Ask: where does docker pull python:3.13-slim go when you name no registry? Sources: OCI Distribution Specification v1.1; Amazon ECR User Guide, Private registry authentication.

Volumes, bind mounts and tmpfs

Files written to the container's writable layer are deleted with the container. A named volume keeps data that must outlive a container, such as the Postgres data directory in Lab 03 (Docker, n.d.).

Choose the mount type by asking who manages the data and how long it must last. Docker creates and manages named volumes. They survive docker rm and can be attached to a new container, which is how you upgrade or replace a database container. In Lab 03 the Postgres volume is called bagtrack-db. A bind mount maps a host path you choose into the container. Bind mounts suit development, because an edit on the host appears inside at once. They also tie the container to one host's folder layout and file ownership. A tmpfs mount is held in memory and never written to disk, which suits scratch files. On Fargate you cannot mount a host path. A task gets ephemeral storage, can mount Amazon EFS file systems, or uses a managed database. On Day 3 these become Kubernetes volumes and PersistentVolumeClaims. Ask: where should Postgres keep its data on Fargate? Sources: Docker documentation, Volumes, Bind mounts and tmpfs mounts.

Bridge networks and container DNS

On a user-defined network, Docker's embedded DNS server at 127.0.0.11 resolves container names to their current IP addresses (Docker, n.d.). Containers on the default bridge network can reach each other only by IP address.

Every Docker host has a default bridge network, docker0, and containers join it unless you name another network. Docker's documentation recommends user-defined networks instead. Containers on one user-defined network can resolve each other by name or network alias. Containers on other networks cannot reach them at all, which gives each application its own scope. In Lab 03 the network is called lab, and bag-api reaches Postgres by the name bagtrack-db. Names matter because IP addresses change whenever a container is recreated. The board's nginx configuration proxies /api/ to the name bag-api, so it keeps working after bag-api is replaced. Compose creates a user-defined network for each project, which is why services can use each other's names. On ECS with awsvpc networking each task gets its own network interface, and the containers in one task talk over localhost. Kubernetes gives each Service a DNS name. Ask: which name should the board use for bag-api once both run in Compose? Source: Docker documentation, Networking overview and Bridge network driver.

Publishing ports

-p 8080:8080 publishes port 8080 on every host address and forwards it to port 8080 in the container (Docker, n.d.). Publish only what users need, and use -p 127.0.0.1:8080:8080 to limit a port to the host itself.

A container's ports are reachable from the host and from containers on the same network. Other machines cannot reach them. -p host:container asks Docker to forward a host port to a container port, and the two numbers can differ, as in -p 8081:8080. Docker's documentation says publishing is insecure by default, because without an address the port opens on every interface of the host. The EXPOSE instruction only documents a port, and -P publishes every exposed port on a random high port. In BagTrack only the board needs to be published. It serves the page and proxies /api/ to bag-api over the network, so bag-api and Postgres stay private. On ECS with awsvpc networking, the load balancer sends traffic to the task's own IP address and container port. Ask: why should Postgres's port stay unpublished? Sources: Docker documentation, Port publishing and mapping; Amazon ECS Developer Guide, task networking.

Restart policies

PolicyDocker restarts the container
noNever. This is the default.
on-failure[:N]After it exits with a non-zero code, up to N times
alwaysWhenever it stops, and again when the Docker daemon starts
unless-stoppedLike always, except after you stop it yourself

A restart policy reacts only to the main process exiting. If you stop a container by hand, Docker does not restart it until the daemon restarts or you start it again (Docker, n.d.).

Restart policies are Docker's simplest form of self-healing. They act only on exits. If the process crashes or is killed, Docker starts the same container again, with the same writable layer and configuration. They do not act on a container that is still running but no longer answering, and that is what health checks are for. always and unless-stopped also bring containers back after the VM reboots, because the Docker service starts at boot and starts them again. Use on-failure for jobs that should retry but stop once they succeed. In Lab 03 the main process exits, Docker restarts the container, and docker inspect shows a RestartCount of 1. ECS services and Kubernetes Deployments have their own ways to replace failed containers, which you meet on Days 2 and 3. Ask: which policy suits Postgres on a single server? Source: Docker documentation, Start containers automatically.

Health checks

# Mark Postgres healthy once it accepts connections
docker run -d --name db \
  --health-cmd "pg_isready -h localhost -U postgres" \
  --health-interval 10s --health-retries 3 \
  -e POSTGRES_PASSWORD=example \
  public.ecr.aws/docker/library/postgres:17

# The STATUS column shows (healthy) or (unhealthy)
docker ps

# In a Dockerfile, the same check becomes part of the image
HEALTHCHECK --interval=10s --retries=3 \
  CMD pg_isready -h localhost -U postgres

Docker marks a container unhealthy after the set number of failed checks in a row, and it does not restart it. ECS runs only the health check in the task definition and replaces unhealthy tasks in a service (Amazon Web Services, n.d.).

A process can be running and still be useless, for example a web server whose database connection is gone. A health check runs a command inside the container at each interval. Exit code 0 means healthy and 1 means unhealthy. After the configured number of failures in a row, the status changes to unhealthy. pg_isready is a client tool in the Postgres image that reports whether the server accepts connections. Docker itself only records the status. Compose uses it in Lab 05 to start bag-api after the database is healthy. ECS ignores the HEALTHCHECK in an image and uses the healthCheck in the container definition. For tasks in a service, an unhealthy essential container makes ECS stop and replace the task. Kubernetes uses its own liveness and readiness probes, which call bag-api's /healthz and /readyz on Day 3. In Lab 03, a wrong database password makes /readyz return 503 while /healthz still returns 200. Ask: why would /readyz make a poor liveness check? Sources: Docker documentation, Dockerfile reference; Amazon ECS API Reference, HealthCheck.

A troubleshooting checklist

CommandWhat it tells you
docker ps -aWhether the container is running, and its exit code
docker logs --tail 50 webWhat the application printed before it failed
docker inspect webState, OOMKilled, health, mounts, networks and environment
docker exec -it web shFiles, settings and DNS as the container sees them
docker eventsWhat Docker did and when, such as restarts, kills and health changes

Read the status and the logs before you change anything.

Teach this as a fixed order. docker ps -a shows stopped containers too, with the exit code in the STATUS column. docker logs works on stopped containers, so read the logs before you remove anything. docker inspect answers most configuration questions: the exact command, environment variables, mounts, networks, the restart count, OOMKilled and the last health check results. docker exec starts a second process inside a running container. From there, getent hosts db checks DNS and env shows the variables. Images without a shell need nsenter from the host instead. docker events streams what the daemon does, which helps with containers that restart in a loop. Example from Lab 03: bag-api gets a wrong database password. The container keeps running, /healthz returns 200 and /readyz returns 503. docker logs shows a warning that the database is not reachable, and docker inspect shows the DATABASE_URL the container was given. Ask: a container restarts every few seconds, so which command do you run first? Source: Docker documentation, Docker CLI reference.
