How the Day 1 concepts connect

The commands on the arrows are the ones you ran in Labs 01 to 03.

This is Day 1 on one slide. Walk it from left to right. A Dockerfile is a list of build instructions. docker build turns it into an image, which is a stack of read-only layers plus a configuration with the entrypoint, environment and user. docker push sends the image to a registry, which stores it by tag and by digest, and docker pull fetches it. docker run creates a container, which is an ordinary Linux process with its own namespaces, cgroup limits and a thin writable layer. Why image size matters

  • Fargate pulls the whole image for each new task, because it caches no images (Amazon Web Services, n.d.).
  • Every package in an image can bring vulnerabilities, even when the application never uses it.
  • Shells, package managers and compilers give an attacker tools after a break-in.
  • A smaller image gives a shorter vulnerability report to review.
  • Registries keep every version you push, and each node stores its own copy.

A large image slows scale-out and the replacement of failed tasks.

Start with start time, because it matters most on ECS with Fargate. AWS documents that every Fargate task runs on its own single-use instance and that images and layers are not cached there. Each task pulls the whole image, and the pull time is part of the start time. When a service scales out at a busy hour, or replaces a failed task, every new task waits for that download. On EC2 container instances and Kubernetes nodes a cached image helps, but only on nodes that pulled it before. The other reasons are security and cost. Every package can bring a CVE, and tools such as a shell or curl help an attacker. Example: on the lab machine, the scanner's final image is 9.5 MB, and its build stage is 1.41 GB. Ask: how big is the largest image your team deploys? Source: Amazon Web Services. (n.d.). Linux containers on Fargate container image pull behavior. How a multi-stage build works

Only the final stage becomes the image. The build stage stays in the build cache of the machine that ran the build.

Multi-stage builds arrived in Docker 17.05 in 2017. Before that, teams used the builder pattern, with one Dockerfile for the compilers, a script that copied the binary out of a container, and a second Dockerfile for the runtime image. Multi-stage builds put both in one file. Each FROM starts a new stage, and COPY --from copies files out of an earlier stage. BuildKit builds only the stages that the final stage needs. Example: the scanner. On the lab machine its build stage is 1.41 GB, because it holds the Go toolchain, the standard library and tools such as git. The final image holds one static binary. It is 9.5 MB, and Trivy finds nothing in it. The build stage is never pushed. Ask: what would the final stage need for a Java service? (A Java runtime, without the JDK and Maven.) Source: Docker. (n.d.). Multi-stage builds. docs.docker.com/build/building/multi-stage/

A multi-stage Dockerfile for the scanner

FROM public.ecr.aws/docker/library/golang:1.26 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/scanner .

FROM scratch
COPY --from=build /out/scanner /scanner
USER 65532:65532
ENTRYPOINT ["/scanner"]

CGO_ENABLED=0 makes Go produce a static binary, which needs no files from the base image. USER takes numbers here, because scratch has no /etc/passwd to look up a name.

Read it from top to bottom. The first FROM names its stage build. COPY . . brings in the scanner source, and the .dockerignore file from Day 1 keeps other files out. The go build line turns cgo off, so Go uses its own code instead of calling the C library, and the result is a static binary. The second FROM starts again from scratch, an image with no files at all. COPY --from=build takes one file from the first stage. USER sets a numeric user and group. 65532 is the nonroot user of the distroless images, and any unused number works. There is no shell in this image, so ENTRYPOINT must use the exec form. Ask: what happens if you run docker exec with sh on this container? (It fails, because there is no sh.) Source: Docker. (n.d.). Multi-stage builds. docs.docker.com/build/building/multi-stage/

Alpine Linux and musl libc

  • Alpine Linux uses musl libc and BusyBox, and its base image is about 5 MB (Docker, n.d.).
  • Most prebuilt Linux software, including manylinux Python wheels, is built against glibc.
  • When a package has no musllinux wheel, pip builds it from source, which needs compilers in the image.
  • Software that relies on glibc behaviour can fail on musl (Docker, n.d.).

For Python services, the slim Debian image avoids these problems.

Alpine is popular because it is small. On the lab machine, python:3.13-alpine is 70.5 MB and python:3.13-slim is 178 MB. The cost is the C library. musl is a different implementation of the C standard library from glibc, which Debian and Ubuntu use. Binaries linked against glibc do not run on musl. For Python this shows up in wheels. The manylinux wheels on PyPI are built for glibc, so on Alpine pip looks for musllinux wheels, and if a package has none, pip builds it from source. That needs gcc and headers in the image, slows the build and can make the result bigger than slim. Docker's image notes warn that software can run into issues depending on its libc assumptions. Alpine is a good fit for small tools and for software built for musl. Ask: has anyone had a build break after a switch to Alpine? Source: Docker. (n.d.). Docker Official Images: python, image variants. hub.docker.com/_/python

Static and dynamic binaries

The file and ldd commands show how a binary is linked. A static binary that calls HTTPS services also needs CA certificates copied into scratch.

This slide explains why the scanner can run on scratch and the Python interpreter cannot. A dynamically linked program does not contain the C library. When it starts, the kernel first runs the dynamic loader named in the binary, and the loader finds and maps libc and the other shared libraries. All of those files must exist in the image. A statically linked program has the library code compiled in, so the kernel can run it in an empty filesystem. Show it on the VM. Run file and ldd on /usr/bin/python3, then on the scanner binary. ldd reports that the scanner is not a dynamic executable. scratch also has no CA bundle, no time-zone data and no /etc/passwd, so copy in what the program needs. Ask: does the scanner need CA certificates? (No. It calls bag-api over plain HTTP.) Sources: Kerrisk, M. (n.d.). ld.so(8). Linux manual pages. man7.org. Docker. (n.d.). BuildKit cache and secret mounts

# syntax=docker/dockerfile:1
FROM public.ecr.aws/docker/library/python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    --mount=type=secret,id=pipconf,target=/etc/pip.conf \
    pip install -r requirements.txt
COPY bagtrack/ bagtrack/

# Build with: docker build --secret id=pipconf,src=$HOME/.config/pip/pip.conf .

The cache mount keeps pip's downloads on the builder between builds. The secret file exists only for the duration of that RUN instruction (Docker, n.d.).

BuildKit has been Docker's default builder since Engine 23.0. It adds mounts that exist only while one RUN instruction runs. A cache mount keeps a directory, here pip's download cache, on the builder between builds. When requirements.txt changes, the layer cache must rerun the instruction, but pip reuses the packages it downloaded before. A secret mount gives the instruction a file, here a pip.conf that points at a private package index with a token, and removes it afterwards. Neither mount is saved in a layer. Docker's documentation says that build arguments and ENV values persist in the final image, where anyone who pulls it can read them. bag-api has no private packages. This slide shows the pattern for teams that use a private repository such as AWS CodeArtifact. Ask: in a pipeline, where would the token come from? Source: Docker. (n.d.). Build secrets; Optimize cache usage in builds. docs.docker.com/build/

These are the commands for Lab 04. docker image ls shows each image and its size. Root in a container is root on the host

Capabilities and namespaces limit a root process, but any host file it can reach is open to root (Docker, n.d.). A user namespace maps container user IDs to unprivileged host IDs (Kerrisk, n.d.).

Containers share the host kernel, and the kernel identifies processes by numeric user ID. Without a user namespace, user 0 in the container is user 0 on the host. Docker reduces the risk. It drops most capabilities, applies seccomp and AppArmor profiles, and uses namespaces to hide the rest of the system. But if the process reaches a host resource, through a bind mount of a host directory, the privileged flag or a kernel bug, it acts as root there. With a user namespace, the kernel maps user 0 inside to an unprivileged ID outside, for example 100000 from the range in /etc/subuid. Check your own images with docker image inspect and the format string for .Config.User. An empty answer means root. Ask: which BagTrack images run as root right now? Sources: Docker. (n.d.). Docker Engine security. docs.docker.com/engine/security/. Kerrisk, M. (n.d.). user_namespaces(7). Linux manual pages. man7.org

Access to the Docker socket is root access to the host

$ docker run --rm -it -v /:/host public.ecr.aws/docker/library/alpine chroot /host
# id -u
0

Docker's documentation warns that the docker group grants root-level privileges (Docker, n.d.). Portainer and Harness Open Source mount this socket on your lab VM, so treat their logins as root logins.

The Docker daemon runs as root and does whatever its API asks. Anyone who can write to /var/run/docker.sock can ask it to start a container that mounts the host's root directory, then chroot into it. The result is a root shell on the host without a password or sudo. Docker's documentation says that only trusted users should control the daemon, and the post-installation guide warns that the docker group grants root-level privileges. If your user is in the docker group on the lab VM, you already have this power. Two tools in this course mount the socket. Portainer uses it to manage containers, and Harness Open Source uses it to start pipeline step containers. Anyone who can log in to them, or run a pipeline step that reaches the socket, has root on the VM. In Lab 06 the pipeline's build step mounts the socket as well. Ask: which tools in your CI or monitoring stack mount the Docker socket? Source: Docker. (n.d.). Docker Engine security: Docker daemon attack surface; Linux post-installation steps. docs.docker.com

Running the process as a non-root user

FROM public.ecr.aws/docker/library/python:3.13-slim
RUN useradd --system --uid 10001 --no-create-home bagtrack
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY bagtrack/ bagtrack/
USER 10001
EXPOSE 8000
CMD ["uvicorn", "bagtrack.main:app", "--host", "0.0.0.0", "--port", "8000"]

COPY makes root the owner of the files, so the app user can read its code but cannot change it. A numeric ID also lets Kubernetes verify that the container does not run as root.

This is the most useful single change for most images. Create a user in the image, copy the code in as root, then switch with USER. The process starts as that user, so a bug in bag-api gives an attacker an unprivileged account instead of root. Pick a number above the range the base image uses. 10001 is a common choice. The bag-api Dockerfile in Lab 04 follows this pattern and adds a HEALTHCHECK. The CIS Docker Benchmark recommends a dedicated non-root user for containers. If the app must write files, give it one writable directory or a tmpfs, and leave /app owned by root. Ports below 1024 are traditionally privileged, which is one reason the board uses an unprivileged nginx image on port 8080. Ask: what breaks if bag-api from Lab 03 runs as user 10001? (Usually nothing, because it listens on port 8000 and writes no files.) Sources: Center for Internet Security. (n.d.). CIS Docker Benchmark. cisecurity.org. Docker. (n.d.). Dockerfile reference: USER. docs.docker.com

Restricting a container at run time

docker run optionEffect
--read-onlyMounts the container's root filesystem read-only
--tmpfs /tmpAdds a writable directory in memory for temporary files
--cap-drop ALLRemoves every Linux capability; add back only what the app needs with --cap-add
--security-opt no-new-privilegesStops setuid programs from raising the process's privileges

The CIS Docker Benchmark recommends a read-only root filesystem, restricted capabilities and no-new-privileges (Center for Internet Security, n.d.). Compose and Kubernetes have a matching setting for each option.

Each option removes one thing an attacker could use. A read-only root filesystem stops anyone from changing the app's code or adding new programs. A tmpfs on /tmp gives the app room for temporary files. Dropping all capabilities removes powers that Docker's default set still grants, such as changing file ownership or opening raw sockets. Most web services need none of them. no-new-privileges sets a kernel flag so that setuid programs such as su cannot raise the process's privileges. --user overrides the image's user, which helps with images you did not build. In Lab 04 you run bag-api with all of these and check that it still answers /healthz. When something breaks, the error usually names the cause, such as Read-only file system. Ask: which of these options would stop the socket attack from two slides ago? (None of them. The socket controls the daemon itself.) Sources: Center for Internet Security. (n.d.). Rootless mode also guards the host against vulnerabilities in the daemon and the container runtime (Docker, n.d.).

Both modes use user namespaces, which map a range of user IDs inside the namespace to a different range outside. With userns-remap, the daemon still runs as root, but each container's root maps to an unprivileged ID from the dockremap entry in /etc/subuid. A process that escapes then has the rights of an unused, unprivileged user. In rootless mode, the daemon itself runs as your user inside a user namespace. Root in a container maps to your own user ID, and other IDs map to your subordinate range. Both modes have limits. userns-remap cannot share the host's PID or network namespace, and rootless mode needs extra setup to bind ports below 1024. Rootless mode suits developer machines and build hosts. Ask: who uses Podman? It runs rootless when an ordinary user starts it. Sources: Docker. (n.d.). What a vulnerability scanner reports

A CVE ID names one publicly disclosed vulnerability (CVE Program, n.d.). CVSS rates its severity on a scale from 0.0 to 10.0 (FIRST, 2019).

A scanner such as Trivy does not run the image. It reads two kinds of files. The first is the package database of the operating system, such as dpkg on Debian or apk on Alpine. The second is the metadata of language packages, such as Python's installed packages or the module list that Go records in each binary. It compares each package version with advisory data from the Linux distributions, the GitHub Advisory Database and the US National Vulnerability Database. Each finding names a CVE, the installed version, the fixed version if one exists, and a severity. The CVE Program has assigned these IDs since 1999. FIRST maintains CVSS, which turns the properties of a vulnerability into a score. Example: the scanner image has no operating-system packages, so Trivy checks only the Go version and modules in the binary. Ask: why can the same image show new findings next month? (The advisory data changes.) Sources: CVE Program. (n.d.). About the CVE Program. cve.org. FIRST. (2019). CVSS v3.1 specification document. first.org/cvss. Aqua Security. (n.d.). Trivy documentation. trivy.dev

Severity describes how bad a vulnerability could be in general. It cannot know how you use the package. Software bills of materials

  • An SBOM lists the components of an artifact, with each component's name, version and often its licence.
  • CycloneDX, from OWASP, and SPDX, from the Linux Foundation, are the two common formats (CycloneDX, n.d.; SPDX, n.d.).
  • SPDX is also the international standard ISO/IEC 5962:2021.
  • Trivy writes both formats, for example with trivy image --format cyclonedx bag-api:1.0.
  • When a new CVE appears, a search of stored SBOMs shows which images contain the affected package.
An SBOM is an ingredient list for software. The two formats you will meet are CycloneDX, an OWASP project started in 2017, and SPDX, a Linux Foundation project that is also the standard ISO/IEC 5962:2021. Both are JSON or XML files that list packages with names, versions and identifiers such as package URLs. Their value shows on the day a new vulnerability is announced. In December 2021, when Log4Shell was disclosed, many teams spent days finding out which of their images contained Log4j. With an SBOM stored for every image, that question becomes a search. Signing and provenance

A signature shows who published an image (Sigstore, n.d.). Provenance records who built the image, with which process and from which inputs (SLSA, 2023).

A scan lists what is inside an image. Signing and provenance record who published it and how it was built. cosign, from the Sigstore project, signs the image digest and stores the signature in the registry next to the image. By default, Sigstore ties the signature to an identity, such as the pipeline's OIDC token, through a short-lived certificate, and records it in a public transparency log. Provenance is a signed statement about the build. It records which builder ran it, from which repository and commit, and with which parameters. SLSA, an OpenSSF project, defines build levels. Level 1 means provenance exists, level 2 adds a hosted build platform that signs it, and level 3 adds a hardened build platform. At deploy time, a policy checks the signature and the provenance and refuses images that fail. The labs do not sign images. Ask: what would stop a laptop-built image from reaching production where you work? Sources: Sigstore. (n.d.). sigstore.dev. SLSA. (2023). Supply-chain Levels for Software Artifacts, v1.0. slsa.dev

The Compose model

One compose.yaml describes the services, the network and the volume. docker compose up creates them and starts the containers in dependency order (Docker, n.d.).

Compose describes a multi-container application in one YAML file. It began as Fig, from a company called Orchard, which Docker acquired in 2014. Version 1 was a Python program called docker-compose. Version 2 is a Go plugin of the Docker CLI, run as docker compose, and version 1 stopped receiving updates in 2023. The file format is now an open specification. Each service becomes one or more containers. Compose creates a default network for the project, and each service is reachable by its name, which is why the board's nginx can proxy /api/ to bag-api. With --scale scanner=3, Compose runs three scanner containers, and the name scanner resolves to all three. Ask: what happens to the db-data volume when you run docker compose down? (It stays, unless you add -v.) Source: Docker. (n.d.). Docker Compose documentation. docs.docker.com/compose/

Start order with depends_on and healthchecks

services:
  db:
    image: public.ecr.aws/docker/library/postgres:17
    environment: { POSTGRES_USER: bagtrack, POSTGRES_PASSWORD: bagtrack-dev-pw, POSTGRES_DB: bagtrack }
    volumes: [ "db-data:/var/lib/postgresql/data" ]
    healthcheck:
      test: [ "CMD", "pg_isready", "-U", "bagtrack" ]
  bag-api:
    build: ./bag-api
    environment:
      DATABASE_URL: postgresql://bagtrack:bagtrack-dev-pw@db:5432/bagtrack
    depends_on:
      db: { condition: service_healthy }
volumes: { db-data: {} }

Compose starts bag-api only after the db healthcheck passes (Docker, n.d.). Without a condition, depends_on waits only until the db container has started.

This is a trimmed part of the file you write in Lab 05. The db service uses the official Postgres 17 image from ECR Public. Its user, password and database name are set in the file, and its data is kept in the named volume db-data. The healthcheck runs pg_isready, which succeeds once Postgres accepts connections. bag-api is built from its folder, and its DATABASE_URL uses the host name db, which is the service name. depends_on with the condition service_healthy makes Compose wait for that healthcheck before it starts bag-api. The short form, depends_on with a list, only waits for the db container to start, and Postgres needs more time before it accepts connections. bag-api's /readyz endpoint still matters, because depends_on only affects start-up and the database can fail later. The password is a development value for a lab database with no real data. Ask: what else in BagTrack should wait for bag-api? Source: Docker. (n.d.). Control startup and shutdown order in Compose. docs.docker.com/compose/

Values in .env reach a container only through environment or env_file (Docker, n.d.).

These features let one project serve several situations without copies of the file. environment and env_file set variables inside containers. That is how bag-api gets DATABASE_URL, HUB and APP_VERSION. The .env file next to compose.yaml is different. Compose reads it to fill placeholders in the file itself, such as a password that should stay out of Git, and the values reach a container only where the file passes them on. Keep .env out of Git. Profiles mark optional services. A service with the profile debug starts only with --profile debug or the COMPOSE_PROFILES variable. Override files are the main tool for development. docker compose up reads compose.yaml, then compose.override.yaml if it exists, and merges them. With -f you name the files and their order yourself, for example a CI file without bind mounts. Ask: which settings should differ between your laptop and CI? Source: Docker. (n.d.). The bind mount puts your working copy of the code in place of the image's copy. uvicorn --reload restarts the app each time a file changes.

Amazon ECS concepts

A task definition is a versioned JSON description of one or more containers (Amazon Web Services, n.d.). A task is one running copy of a task definition.

Map ECS onto what you know. A task definition is like a Compose file for one group of containers. It lists images, CPU and memory, ports, environment, secrets, log settings and IAM roles. It is versioned. Each change registers a new revision, such as bag-api:7, and old revisions stay available for rollback. A task is a running copy of a revision, one or more containers that start and stop together, like a Pod in Kubernetes. A service keeps the desired number of tasks running, replaces tasks that stop or fail health checks, rolls out new revisions and registers tasks with a load balancer. A cluster groups the capacity where tasks run. With Fargate, AWS supplies that capacity. United's Digital Technology teams chose ECS with Fargate in 2019 and 2020, when Kubernetes was harder to run, and they also use EKS. Ask: which ECS services does your team own? Source: Amazon Web Services. (n.d.). Amazon ECS Developer Guide: Amazon ECS components. docs.aws.amazon.com/AmazonECS/

Fargate and EC2 launch types

FargateEC2

IsolationEach task runs on its own single-use instance (Amazon Web Services, n.d.)Tasks share an instance and its kernel
BillingThe vCPU and memory each task requestsThe instances, busy or idle
Network modesawsvpc onlyawsvpc, bridge, host or none
Image cacheNone; each task pulls its imagesInstances reuse layers they have already pulled

Both launch types run the same kind of task definitions and services.

The launch type decides who runs the servers under your tasks. With EC2, you run container instances, which are ordinary EC2 machines with the ECS agent, usually in an Auto Scaling group. You choose instance types, patch the machine image and pack tasks onto instances, and several tasks share one kernel. With Fargate, AWS supplies a single-use, single-tenant instance for every task, so tasks never share a kernel, and you pay for the CPU and memory each task requests. Fargate requires the awsvpc network mode and task-level CPU and memory values. It has no image cache, which links back to the image-size slide. EC2 still makes sense for GPUs, special instance types or steady, dense workloads. Ask: what do you give up with Fargate? (Host access, daemon settings and privileged containers.) Source: Amazon Web Services. (n.d.). Amazon ECS Developer Guide: launch types; Fargate task definition differences. docs.aws.amazon.com/AmazonECS/

Task networking with awsvpc

With awsvpc, each task gets its own elastic network interface and private IP address (Amazon Web Services, n.d.). Containers in one task share that interface and reach each other on localhost.

awsvpc is the network mode that Fargate requires. ECS creates an elastic network interface for each task in a subnet you choose, and the task gets a private IP address from that subnet, as an EC2 instance would. Security groups attach to that interface, so rules can differ per service. For example, only the load balancer may reach bag-api on port 8000, and only bag-api may reach the database. Inside a task, the containers share one network namespace, so a sidecar such as a log router reaches the app on localhost. In Compose, each container has its own address on a Docker bridge network, and containers find each other by DNS name. Between ECS services, you use a load balancer, Service Connect or Cloud Map instead. Each task uses one address, so subnets must be large enough for scale-out. Ask: who manages subnets and security groups in your teams? Source: Amazon Web Services. (n.d.). Amazon ECS Developer Guide: task networking for Fargate. docs.aws.amazon.com/AmazonECS/

Task execution role and task role

Containers receive credentials for the task role only (Amazon Web Services, n.d.). The execution role's permissions stay with ECS and Fargate.

Two IAM roles confuse almost everyone at first. The task execution role is used by the ECS agent and Fargate around your code. It pulls the image from ECR, fetches secret values from Secrets Manager or SSM Parameter Store, and sends container logs to CloudWatch Logs. The task role is what your application code uses. The AWS SDK inside the container picks up its temporary credentials automatically. If bag-api needed to write a report to S3, that permission would go in the task role. The permission to read the database secret goes in the execution role, because ECS reads the secret and injects it at start. A task that fails to start with an image pull error points to the execution role, or to the network path to ECR. Ask: which role needs permission to send messages to an SQS queue? (The task role.) Source: Amazon Web Services. (n.d.). Amazon ECS Developer Guide: task execution IAM role; task IAM role. docs.aws.amazon.com/AmazonECS/

A service behind an Application Load Balancer

With awsvpc, the target type must be ip, because each task has its own address (Amazon Web Services, n.d.). The service registers new tasks and replaces tasks that fail the health check.

This is how traffic reaches an ECS service. An Application Load Balancer has a listener, for example HTTPS on port 443, with rules that forward requests to a target group. The ECS service owns the registration. When it starts a task, it registers the task's IP address and port in the target group. When it stops a task, it deregisters it and lets open connections drain. The target type must be ip with awsvpc. The load balancer health-checks every target, and the service replaces tasks that stay unhealthy. Choose the health check path with care. bag-api's /readyz checks Postgres. If the load balancer used it, a database outage would mark every task unhealthy, and ECS would keep replacing containers that work. /healthz checks only the process. Ask: where do you see the same idea on Day 3? (A Kubernetes Service and its EndpointSlices.) Source: Amazon Web Services. (n.d.). Why build images in a CI pipeline

  • Every build starts from a clean checkout in the same environment, so results repeat.
  • Dockerfile changes go through pull requests and review like any other code.
  • Every image is linted, tested and scanned before anyone can deploy it.
  • Each image tag leads back to the commit and the pipeline run that built it.
  • Registry credentials stay in the CI system instead of on laptops.

Build each image once and deploy that same image to every environment (Humble and Farley, 2010).

Why not build on a laptop and push? A laptop build depends on what is on that laptop, such as cached layers, local files, a different Docker version or uncommitted changes. A pipeline starts from a clean checkout of one commit, so two runs of the same commit give the same result. It makes review possible, because a Dockerfile change is a pull request like any other change. It makes the checks unavoidable, because lint, tests and the scan run every time. It also keeps the registry password in one place. Humble and Farley's Continuous Delivery, from 2010, adds the principle behind promotion. You build your binaries once and deploy the same artifact to every environment. At United, deployments run in the Harness platform and images are stored in Amazon ECR. Ask: where are the images for your team's services built today? Source: Humble, J., and Farley, D. (2010). Continuous Delivery. Addison-Wesley.

Pipeline stages for an image

A failed stage stops the run, so later stages never start. The cheapest checks run first.

This is the order the Lab 06 pipeline follows. Lint comes first because it is the cheapest check. hadolint parses the Dockerfile, applies rules such as pinning base image versions and not ending as root, and runs ShellCheck on RUN commands. Tests come next, with pytest for bag-api and go test for the scanner, each in its own language container. Then the image is built and scanned with Trivy, and the run fails on critical findings. Push comes last, so an image that fails the scan never reaches the registry. Lab 06 uses separate build, scan and publish steps in this order. Its first run stops at the scan of the board image, because the board's base image has critical vulnerabilities that already have fixes. Ask: which steps would you run on every pull request, and which only on the main branch? Sources: hadolint. (n.d.). Haskell Dockerfile Linter. github.com/hadolint/hadolint. Harness. (n.d.). Treat every tag except latest as immutable. Amazon ECR can enforce this with tag immutability on a repository (Amazon Web Services, n.d.).

A tag is a name that can move. A digest is a hash of the content. Tags are for people and tools. Promoting one digest through environments

Each environment runs the same digest, so production runs the image that passed the tests (Humble and Farley, 2010). Deploying by digest stops a moved tag from changing what runs.

Promotion moves one artifact through the environments, and nothing is rebuilt on the way. A rebuild can pull a newer base image or package, so it produces a different image, even from the same commit. To deploy by digest, use an image reference that ends in @sha256 and the hash, which names the content. Settings that differ between environments, such as database addresses and secrets, come from the environment at run time. The Harness platform models this with services, environments and approvals. Harness Open Source has no deployment model, so on Day 3, in Lab 08, you roll out an image from this pipeline to Kubernetes yourself. Ask: is the image that reaches production in your process the same one QA tested? Source: Humble, J., and Farley, D. (2010). Continuous Delivery. Addison-Wesley.

How Harness Open Source runs a pipeline

Each step runs in its own container on the server's Docker engine (Harness, n.d.). Stages do not share files with each other.

Harness Open Source was first released in 2023 as Gitness, the successor to Drone, the CI system that Harness acquired in 2020. It combines Git hosting, pull requests and pipelines in one container. A pipeline is a YAML file in the repository under .harness. A stage of type ci clones the repository into a workspace, and every step in the stage runs in its own container with that workspace as its working directory. So each step can use its own image, such as hadolint, Python, Go, the Docker CLI or Trivy, and all of them see the same files. Stages do not share files at all. The server starts these containers through the Docker socket it mounts, which links back to the security lecture. The open-source version has known limits. Secrets are not masked in logs, steps in a parallel group run one after another, and there is no step cache. Ask: what does each step container need installed? Source: Harness. (n.d.). Harness Open Source documentation: pipelines, stages, run steps. developer.harness.io/open-source/

The pipeline runs build, scan and publish in that order, so an image that fails the scan is never pushed. A non-zero exit code fails the run step, and the pipeline stops there.

Read the command one option at a time. The step runs in the Trivy image, public.ecr.aws/aquasecurity/trivy:0.76.1, with the Docker socket mounted. --image-src docker makes Trivy read the image from the machine's Docker engine, where the build step left it, so the scan happens before anything is pushed. --severity CRITICAL limits the report to critical findings. --ignore-unfixed hides findings that have no fixed version, because a rebuild cannot fix those. --exit-code 1 makes Trivy exit with code 1 when any finding remains, and a run step that exits with a non-zero code fails. How teams handle scan findings

  • Start with a rebuild on the newest base image and an update of the affected packages.
  • Record an accepted risk in .trivyignore, with a reason and an expiry date (Aqua Security, n.d.).
  • Review accepted risks before they expire, because the pipeline fails again on that date.
  • Rebuild and rescan released images on a schedule, because new CVEs appear for unchanged images.
  • Agree in advance which severities fail the build and who may accept a risk.
Teams that scan every build need an agreed way to deal with findings. Without one, every new CVE blocks all builds until someone decides what to do. Start with a rebuild on the newest base image, which clears every finding whose fix is already in that base. When no fix exists and the risk is acceptable, record it in .trivyignore with the CVE ID, a comment that explains why, and an expiry date in the form exp:2026-12-31. Trivy ignores that CVE until the date. After it, the pipeline fails again, which forces a review. Images that nobody changes still collect new CVEs, so rebuild and rescan released images on a schedule. Decide in advance which severities fail the build and who may accept a risk, and write the decision down. Ask: who signs off on an accepted risk in your team today? Source: Aqua Security. (n.d.). Trivy documentation: filtering, .trivyignore. trivy.dev
